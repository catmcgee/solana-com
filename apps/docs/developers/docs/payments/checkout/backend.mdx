The checkout in the browser gives you a signature. Your server takes that
signature, fetches the transaction from the network, and checks that it paid
you, in USDC, the right amount, for this order. Only then does it mark the
order paid. This step builds that server in a project on your machine and runs
it against a local test network or devnet.

## 1. Create the project

You need Node.js 20.18 or later. Create a project folder, `solana-payments`,
with a `checkout` folder inside it. Every file in this tutorial goes in
`checkout/`, and you run every command from `solana-payments`. The
[Paywall an endpoint](/developers/docs/payments/paywall-api) tutorial adds a
`paywall-api/` folder next to it in the same project, so the two tutorials
never overwrite each other's files.

```bash Terminal
mkdir -p solana-payments/checkout && cd solana-payments
npm init -y && npm pkg set type=module
npm install @solana/kit @solana-program/token
npm install --save-dev tsx
```

`"type": "module"` lets the scripts use top-level `await`. `tsx` runs the
TypeScript files directly. The examples are tested with `@solana/kit` 8.4 and
`@solana-program/token` 0.17.

## 2. Verify a payment

## 3. Add a confirm endpoint

The endpoint looks the order up, so it needs somewhere to keep orders. This
in-memory store stands in for your database. Save it as `checkout/orders.ts`:

<OrdersExample />

In production, make `markPaidOnce` a single database transaction with a unique
constraint on the signature and on each order's paid signature, so two
concurrent requests can't both succeed.

The endpoint receives `{ "signature": "…" }` for an order, runs
`verifyPayment`, and marks the order paid. It refuses a signature that was
already used, so one payment can never pay for two orders. Save the Node.js
version as `checkout/server.ts`. It has no framework, and its handler body
ports directly to Express, Fastify, or Hono: read the signature, verify it, mark
it used. The Next.js tab is the same handler as an App Router route file. In a
Next.js app, save it at `app/api/orders/[orderId]/confirm/route.ts` and change
its imports to point at where you keep `config`, `orders` and
`verify-payment`.

<RouteExample />

<Note>
  The endpoint passes the order's reference, which the `@solana/kit` payment
  code attaches to the transfer. `reference` is optional in `verifyPayment`,
  but keep it. Transactions are public, so without a reference anyone who sees
  a payment to your store could submit its signature for their own order of
  the same amount. If your checkout can't attach your reference, also check
  who paid, for example that the signer is the customer's wallet.
</Note>

The output shows the three cases your endpoint must handle:

- **200** for a confirmed payment of the right amount.
- **402 `already used`** when the same signature is sent again.
- **402 `amount mismatch`** when a 2 USDC order was paid with 1 USDC.

## 4. Call it from the checkout

Build the customer's payment with `payStore`, not with the live demo's
`PaymentButton`. `payStore` attaches the order's reference to the transfer,
and this endpoint requires it.

1. When the customer checks out, create the order on your server with a fresh
   reference (`(await generateKeyPairSigner()).address`) and send the order's
   `storeOwner`, `amount`, and `reference` to the browser.
2. In the browser, call `payStore(customer, order)`, where `customer` is the
   wallet's `TransactionSigner` (for example from
   `useWalletAccountTransactionSigner` in
   [`@solana/react`](/developers/docs/clients/official/javascript)). It resolves to the transaction signature once the payment is
   confirmed.
3. `POST` that signature to `/api/orders/<order-id>/confirm` with a JSON body
   of `{ "signature": "…" }`.

Show the confirmation page only when the response is `200` with
`"paid": true`. Treat any other response as unpaid, and let the customer
retry.

<Warning>
  This endpoint can't confirm a `PaymentButton` payment. The button builds its
  own transfer and doesn't take your order's reference, so `verifyPayment`
  answers `reference not found` and the endpoint returns `402`. If you use the
  button anyway, you need a different check: drop `reference` from the
  `verifyPayment` call and check instead that the payer is the customer's
  wallet and that the signature hasn't paid for another order. Without the
  reference, anyone who sees a payment to your store on the public ledger could
  submit its signature for their own order of the same amount.
</Warning>

## 5. Run it on your machine

You now have five files in `checkout/`: `config.ts`, `pay.ts`,
`verify-payment.ts`, `orders.ts`, and `server.ts`. This script plays both
sides: it starts the server on port 3000, creates a store wallet and its USDC
account, creates order `order-1001` for 1 USDC, pays it as the customer with
`payStore`, and posts the signature to the confirm endpoint twice. Save it as
`checkout/run.ts`:

<RunExample />

The script pays as the customer with a key file: the file named in
`CUSTOMER_KEYPAIR`, or the Solana CLI default `~/.config/solana/id.json`. If
you already have one (for example from `solana-keygen new`), skip this.
Otherwise save this as `keygen.ts` in `solana-payments`. It writes a new key
file in the same format, a JSON array of 64 bytes, and prints its address:

```ts keygen.ts
import { generateKeyPairSync } from "node:crypto";
import { existsSync, mkdirSync, writeFileSync } from "node:fs";
import { homedir } from "node:os";
import { dirname, join } from "node:path";
import { createKeyPairSignerFromBytes } from "@solana/kit";

// Writes a new key file in the Solana CLI format (64 bytes as a JSON array).
const keyPath = join(homedir(), ".config", "solana", "id.json");
if (existsSync(keyPath)) throw new Error(`${keyPath} exists; not overwriting it`);
const { privateKey, publicKey } = generateKeyPairSync("ed25519");
const bytes = new Uint8Array([
  ...privateKey.export({ format: "der", type: "pkcs8" }).subarray(-32),
  ...publicKey.export({ format: "der", type: "spki" }).subarray(-32),
]);
mkdirSync(dirname(keyPath), { recursive: true });
writeFileSync(keyPath, JSON.stringify([...bytes]), { mode: 0o600 });
console.log(`Address: ${(await createKeyPairSignerFromBytes(bytes)).address}`);
```

```bash Terminal
npx tsx keygen.ts
```

The key file is a private key. Keep it out of version control.

The customer needs SOL for fees and at least 1 USDC on the same USDC mint the
code uses. Pick a network:

<Tabs>
<Tab title="Local (Surfpool)">

1. Install the [Surfpool CLI](/developers/docs/tools/surfpool/toolchain/getting-started)
   and start a local network that copies accounts from devnet, so the devnet
   USDC mint the code uses exists locally. It airdrops SOL to
   `~/.config/solana/id.json` when it starts (create the key file first):

   ```bash Terminal
   surfpool start --network devnet
   ```

2. In another terminal, in `solana-payments`, give the customer 10 test USDC
   with Surfpool's
   [`surfnet_setTokenAccount`](/developers/docs/tools/surfpool/rpc/cheatcodes)
   cheatcode. Replace `<customer address>` with the address of your key file:

   ```bash Terminal
   curl http://127.0.0.1:8899 -s -X POST -H "Content-Type: application/json" -d '
     {"jsonrpc": "2.0", "id": 1, "method": "surfnet_setTokenAccount",
      "params": ["<customer address>", "4zMMC9srt5Ri5X14GAgXhaHii3GnPAEERYPJgZJDncDU",
                 {"amount": 10000000, "state": "initialized"},
                 "TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA"]}'
   ```

3. Point the code at Surfpool:

   ```bash Terminal
   export RPC_URL=http://127.0.0.1:8899
   export RPC_SUBSCRIPTIONS_URL=ws://127.0.0.1:8900
   ```

</Tab>
<Tab title="Devnet">

Leave `RPC_URL` and `RPC_SUBSCRIPTIONS_URL` unset. Paste the customer's
address into the [Solana Faucet](https://faucet.solana.com/) for devnet SOL,
and into [Circle's faucet](https://faucet.circle.com/) with **Solana Devnet**
selected for devnet USDC. Other SOL faucets are listed in
[Airdrops and faucets](/developers/cookbook/development/airdrops-and-faucets).

</Tab>
</Tabs>

Then run the script:

```bash Terminal
npx tsx checkout/run.ts
```

The output under the script above is what it printed on a local Surfpool
network. Expect the same lines with different addresses and signatures: `200`
with `"paid": true` for the payment, then `402` with `already used` for the
same signature sent again. Each run creates a new store wallet, so you can run
it as often as the customer has USDC.

<Note>
  Port 3000 in use? Set another one for the run, for example
  `PORT=3001 npx tsx checkout/run.ts`.
</Note>

repository under `packages/docs-examples/paths/payments/checkout`. The test
starts its own Surfpool network from npm and funds a test customer, so you
need no Surfpool CLI, keys, SOL, or USDC. It also checks that `verifyPayment`
