이 퀵스타트는 `anchor init`로 생성된
[Anchor 프레임워크](https://www.anchor-lang.com/docs) 스타터 프로젝트를
사용합니다. 프로젝트를 로컬에 생성하고, 테스트를 실행하고, 프로그램을 빌드하며,
Anchor가 생성하는 프로그램 코드를 살펴봅니다.

## 사전 요구 사항

시작하기 전에 [Solana 개발 도구를 설치하세요](/docs/intro/installation). 설치
항목에는 Rust, Solana CLI, Anchor CLI가 포함됩니다.

이 템플릿에는 Anchor CLI 버전 1.1.2 이상을 사용하세요. 설치된 버전을 확인하려면:

```bash Terminal
anchor --version
```

<Steps titleSize="h3">

<Step title="프로젝트 생성">

터미널에서 다음 명령어를 실행하세요:

```bash Terminal
anchor init my-program
cd my-program
```

스타터 프로젝트에는 `programs/my-program` 아래에 Solana 프로그램이 하나 포함되어
있습니다. 이 프로그램에는 두 가지 명령어가 있습니다: 카운터 계정을 초기화하는
명령어와 카운터를 증가시키는 명령어입니다.

템플릿의 일부 코드는 일반적인 Solana 프로그램 패턴을 보여줍니다:
[PDA](/docs/core/pda) 계정 주소 도출, SOL을 전송하기 위한 Cross Program
Invocation([CPI](/docs/core/cpi)) 수행, 그리고 조건 실패 시 명령어를 중단하기
위한 커스텀 오류 검사 사용.

</Step>

<Step title="프로그램 빌드">

`anchor build`를 실행하여 스타터 프로그램을 컴파일하세요:

```bash Terminal
anchor build
```

컴파일된 프로그램은 `target/deploy/my_program.so`에 저장됩니다. 프로그램이
배포되면 이 `.so` 파일의 내용이 온체인 계정에 저장됩니다.

</Step>

<Step title="테스트 실행">

기본 테스트를 실행합니다:

```bash Terminal
anchor test
```

이 템플릿의 `Anchor.toml`는 Rust 테스트 명령을 사용합니다:

```toml Anchor.toml
skip_local_validator = true

[scripts]
test = "cargo test"
```

테스트는 컴파일된 프로그램을 [LiteSVM](https://www.litesvm.com/)에 로드하고,
페이어를 생성하여 `initialize` 및 `increment` 명령어를 전송한 후, 카운터
계정 상태를 확인합니다.

`anchor test`를 실행하면 프로그램도 함께 컴파일되므로, 로컬에서 테스트할 때 먼저
`anchor build`를 실행할 필요가 없습니다.

</Step>

<Step title="프로그램 배포">

로컬 테스트는 가장 빠른 피드백 루프입니다. devnet과 같은 네트워크에 배포할
준비가 되었다면, 먼저 빌드한 후 클러스터에 배포하세요.

Solana 프로그램을 배포하려면 SOL이 필요합니다. 프로그램이 계정에 저장되고, 해당
계정은 사용하는 공간에 대한 비용을 지불해야 하기 때문입니다. devnet에서는
[Solana Faucet](https://faucet.solana.com/)을 이용하거나 Solana CLI로 무료
devnet SOL을 요청할 수 있습니다:

```bash Terminal
solana airdrop 2 --url devnet
```

```bash Terminal
anchor build
anchor deploy --provider.cluster devnet
```

</Step>

</Steps>

## 소스 파일

`src` 디렉터리에는 Solana 프로그램이 포함되어 있습니다. Anchor의
[Program Structure](https://www.anchor-lang.com/docs/basics/program-structure)
문서에서는 `declare_id!`, `#[program]`, `#[derive(Accounts)]`,
`#[account]` 등 여기서 사용된 핵심 매크로를 설명합니다. 이 섹션에서는 템플릿
파일들을 살펴봅니다.

### lib.rs

`lib.rs`는 프로그램 진입점입니다. 소스 파일을 연결하고, 프로그램 주소를
정의하며, 사용자가 호출할 수 있는 프로그램 명령어를 정의합니다.

```rust programs/my-program/src/lib.rs wrap
pub mod constants;
pub mod error;
pub mod instructions;
pub mod state;

use anchor_lang::prelude::*;

pub use constants::*;
pub use instructions::*;
pub use state::*;

declare_id!("82sFkffP9wxwpyfZyeaKHH2chQoJPUGsJZSPi9mrUuXd");

#[program]
pub mod my_program {
    use super::*;

    pub fn initialize(ctx: Context<Initialize>) -> Result<()> {
        crate::instructions::initialize::handle_initialize(ctx)
    }

    pub fn increment(ctx: Context<Increment>) -> Result<()> {
        crate::instructions::increment::handle_increment(ctx)
    }
}
```

<Note>
  **`pub mod constants`**

  `pub mod constants`은(는) `constants.rs`을(를) 프로그램 크레이트의 일부로
  만듭니다. 이 파일에는 PDA seed, 전송 금액, 최대 카운터 값과 같은 공유 프로그램
  값이 저장됩니다.

  **`pub mod error`**

  `pub mod error`은(는) `error.rs`을(를) 프로그램 크레이트의 일부로 만듭니다.
  이 파일은 명령어가 유효하지 않을 때 프로그램이 반환할 수 있는 커스텀 오류를
  정의합니다.

  **`pub mod instructions`**

  `pub mod instructions`은(는) `instructions.rs`을(를) 프로그램 크레이트의
  일부로 만듭니다. 해당 파일은 `src/instructions/` 내 명령어별 파일들의 인덱스
  역할을 합니다.

  **`pub mod state`**

  `pub mod state`은(는) `state.rs`을(를) 프로그램 크레이트의 일부로 만듭니다.
  이 파일은 `Counter` account를 포함하여 이 프로그램이 소유한 계정의 데이터
  레이아웃을 정의합니다.

  **`anchor_lang::prelude`**

  `anchor_lang::prelude::_`은(는) Solana 프로그램 정의에 사용되는 Anchor 타입과 매크로를 가져옵니다. 여기에는 `Context`, `Result`, `Pubkey`, `Account`, `Signer`
  및 Anchor 계정 속성이 포함됩니다.

  `pub use` 줄은 하위 모듈의 공개 항목을 크레이트 루트에서 사용할 수 있도록
  합니다. 이를 통해 긴 모듈 경로 대신 `Context<Initialize>`와 같이 명령어
  진입점을 간결하게 유지할 수 있습니다.

  **`declare_id!`**

  `declare_id!`은(는) 프로그램의 주소를 정의합니다. 이 주소는 `Anchor.toml`,
  배포된 program account, 그리고 프로그램을 호출하는 모든 사용자 또는 테스트와
  일치해야 합니다.

  **`#[program]`**

  `#[program]`은(는) Anchor에게 Solana 프로그램 진입점과 명령어 디스패치
  코드를 생성하도록 지시합니다. 이 모듈의 공개 함수들이 사용자가 호출할 수 있는
  명령어가 됩니다.

  **`pub fn initialize`, `pub fn increment`**

  `initialize`와 `increment`은(는) 사용자가 호출할 수 있는 두 가지 명령어
  이름입니다. 각각은 `Context<T>`을(를) 받습니다. `Context` 내부의 타입은
  해당 명령어에 필요한 계정을 정의하며, Anchor는 명령어 실행 전에 해당 계정들을
  검증합니다.

  **`handle_initialize`, `handle_increment`**

  핸들러 함수에는 명령어에 대한 로직이 포함되어 있습니다.
</Note>

동일한 프로그램 주소가 설정과 코드 모두에 나타납니다. `Anchor.toml`는 Anchor에게
클러스터에 배포하거나 호출할 주소를 알려줍니다. `declare_id!`는 보안 검사를
위해 프로그램 내에서 프로그램 주소를 정의합니다.

### constants.rs

`constants.rs`는 공유 값을 한 곳에 보관합니다. 이 템플릿에서
`COUNTER_SEED`는 카운터 PDA를 도출하고, `HELLO_WORLD_LAMPORTS`는 초기화
시 전송되며, `MAX_COUNT`는 증가 전에 확인됩니다.

```rust programs/my-program/src/constants.rs wrap
use anchor_lang::prelude::*;

#[constant]
pub const COUNTER_SEED: &[u8] = b"counter";

#[constant]
pub const HELLO_WORLD_LAMPORTS: u64 = 1;

#[constant]
pub const MAX_COUNT: u64 = 10;
```

<Note>
  **`#[constant]`**

  `#[constant]`는 Anchor에게 해당 값을 프로그램 IDL에 포함하도록 지시합니다.
  이를 통해 중요한 프로그램 상수를 생성된 클라이언트 및 툴링에서 확인할 수
  있습니다.

  **`COUNTER_SEED`**

  `COUNTER_SEED`는 카운터 PDA를 도출하는 데 사용되는 바이트 문자열입니다.
  프로그램과 테스트 모두 이 seed를 사용하므로 별도의 keypair를 저장하지 않고도
  계정 주소에 동의할 수 있습니다. 이 템플릿은 하나의 고정된 seed를 사용하므로
  프로그램에는 하나의 카운터 주소가 있습니다. 실제 프로그램에서는 여러 관련 계정을
  생성하기 위해 사용자 주소나 다른 식별자를 seeds에 포함하는 경우가 많습니다.

  **`HELLO_WORLD_LAMPORTS`**

  `HELLO_WORLD_LAMPORTS`는 `initialize` 내에서 지불자로부터 카운터
  계정으로 전송되는 lamport의 양입니다. 템플릿이 System Program에 대한 CPI를
  시연하고 있기 때문에 의도적으로 매우 작은 값으로 설정되어 있습니다.

  **`MAX_COUNT`**

  `MAX_COUNT`는 `increment`가 검사하는 상한값입니다. 이 값을 여기에 두면
  프로그램, 테스트, 생성된 IDL이 해당 규칙에 대해 하나의 공통된 이름을 공유하게
  됩니다.
</Note>

### state.rs

`state.rs`는 프로그램이 생성하고 소유하는 계정에 대한 커스텀 데이터 타입을
정의합니다. 프로그램은 해당 데이터를 생성, 초기화 및 업데이트하는 명령어를
정의하지만, 카운터 데이터는 프로그램 자체에 저장되지 않습니다. 이는 고유한
주소를 가진 별도의 계정에 저장됩니다.

```rust programs/my-program/src/state.rs wrap
use anchor_lang::prelude::*;

#[account]
#[derive(InitSpace)]
pub struct Counter {
    pub count: u64,
    pub authority: Pubkey,
}
```

<Note>
  **`#[account]`**

  `#[account]`는 Anchor에게 이 구조체가 이 프로그램이 소유하는 온체인 계정에
  저장될 수 있는 데이터임을 알립니다. Anchor는 이를 사용하여 `Counter` 계정을
  직렬화, 역직렬화 및 검증합니다.

  **`InitSpace`**

  `InitSpace`를 사용하면 Anchor가 이 구조체의 필드에 필요한 바이트 수인
  `Counter::INIT_SPACE`를 계산할 수 있습니다. 8바이트의 Anchor 계정 식별자는
  계정이 생성될 때 별도로 추가됩니다.

  **`count`**

  `count`는 계정 데이터 내에 저장된 카운터 값입니다.

  **`authority`**

  `authority`는 카운터를 증가시킬 수 있는 권한이 부여된 주소를 저장합니다.
  `initialize`는 이 주소를 기록하고, `increment`는 동일한 주소의 서명을
  요구합니다.
</Note>

<Columns cols={2}>

    ```rust initialize.rs highlight={4,12-13} wrap
        payer = payer,
        space = 8 + Counter::INIT_SPACE,

        Ok(())
    }
    ```


  </div>

  <div>
    `state.rs`는 `Counter` 계정 데이터를 정의합니다. 명령어 파일은 계정을
    생성하고 업데이트할 때 해당 타입을 사용합니다:

    - `Counter::INIT_SPACE`는 `state.rs`에 정의된
      필드에 맞게 계정 크기를 조정합니다.
    - `count` 및 `authority`는 계정이 초기화될
      때 기록되는 필드 값입니다.
    - `count += 1`는 유효성 검사를 통과한 후 저장된
      카운터 값을 업데이트합니다.
  </div>

### error.rs

`error.rs`는 프로그램의 커스텀 오류를 정의합니다. 이 템플릿에서 오류는 호출자가
카운터를 업데이트할 권한이 없거나 카운터가 이미 `MAX_COUNT`에 도달했을 때
명령어 핸들러가 중단되는 방식을 보여줍니다.

```rust programs/my-program/src/error.rs wrap
use anchor_lang::prelude::*;

#[error_code]
pub enum ErrorCode {
    #[msg("Only the counter authority can update this counter")]
    Unauthorized,
    #[msg("Counter has reached the maximum value")]
    CounterOverflow,
}
```

<Note>
  **`#[error_code]`**

  `#[error_code]`는 Anchor에게 이 변형들을 커스텀 프로그램 오류로 변환하도록
  지시합니다. 클라이언트와 테스트는 원시 오류 코드를 추측하는 대신 해당 오류를
  사용할 수 있습니다.

  **`Unauthorized`**

  `Unauthorized`는 트랜잭션 서명자가 카운터 계정에 저장된 권한자가 아닐 때
  반환됩니다.

  **`CounterOverflow`**

  `CounterOverflow`는 증가 시 프로그램의 `MAX_COUNT` 규칙을 위반하게 될 때
  반환됩니다.
</Note>

    ```rust increment.rs highlight={5,9} wrap

        require_keys_eq!(

            ctx.accounts.authority.key(),
            ErrorCode::Unauthorized,

            ctx.accounts.counter.count < MAX_COUNT,
            ErrorCode::CounterOverflow,
        );

        ctx.accounts.counter.count += 1;
        msg!("Hello, world! Counter is now {}", ctx.accounts.counter.count);
        Ok(())
    }
    ```
  </div>

  <div>
    `error.rs`는 명령어가 반환할 수 있는 오류를 명시합니다:

    - `ErrorCode::Unauthorized`는 서명자가 카운터
      계정에 저장된 권한자가 아닐 때 반환됩니다.
    - `ErrorCode::CounterOverflow`는 카운터가 이미
      `MAX_COUNT`에 도달했을 때 반환됩니다.
  </div>
</Columns>

### instructions.rs

`instructions.rs`는 명령어 파일들을 프로그램 크레이트에 연결하여 `lib.rs`가
`initialize` 및 `increment` 명령어 코드에 접근할 수 있도록 합니다. 각
명령어 파일은 해당 명령어에 필요한 계정과 Anchor가 해당 계정을 검증한 후
실행되는 핸들러 로직을 정의합니다.

```rust programs/my-program/src/instructions.rs wrap
pub mod initialize;
pub mod increment;

pub use initialize::*;
pub use increment::*;
```

<Note>
  **`pub mod initialize`**

  `pub mod` 줄은 `src/instructions/initialize.rs`와
  `src/instructions/increment.rs`를 프로그램 크레이트의 일부로 만듭니다.

  **`pub use initialize`**

  `pub use` 줄은 해당 파일들의 공개 항목을 재내보냅니다. 이를 통해 명령어 계정
  구조체와 핸들러 함수를 `instructions` 모듈을 통해 사용할 수 있게 됩니다.
</Note>

### initialize.rs

`initialize.rs`는 카운터 계정을 생성하는 데 필요한 계정을 정의하고, 계정의 초기
값을 기록합니다. `#[derive(Accounts)]` 구조체는 Anchor
[account constraints](https://www.anchor-lang.com/docs/references/account-constraints)를
사용하여 어떤 계정이 필요한지, 새로운 카운터 계정이 어떻게 생성되는지를
지정합니다.

```rust programs/my-program/src/instructions/initialize.rs wrap
use anchor_lang::prelude::*;

use crate::{constants::*, state::Counter};

#[derive(Accounts)]
pub struct Initialize<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,
    #[account(
        init,
        payer = payer,
        space = 8 + Counter::INIT_SPACE,
        seeds = [COUNTER_SEED],
        bump
    )]
    pub counter: Account<'info, Counter>,
    pub system_program: Program<'info, System>,
}

pub fn handle_initialize(ctx: Context<Initialize>) -> Result<()> {
    ctx.accounts.counter.count = 0;
    ctx.accounts.counter.authority = ctx.accounts.payer.key();

    let cpi_accounts = anchor_lang::system_program::Transfer {
        from: ctx.accounts.payer.to_account_info(),
        to: ctx.accounts.counter.to_account_info(),
    };
    let cpi_ctx = CpiContext::new(anchor_lang::system_program::ID, cpi_accounts);
    anchor_lang::system_program::transfer(cpi_ctx, HELLO_WORLD_LAMPORTS)?;

    msg!("Hello, world! Counter initialized");
    Ok(())
}
```

<Note>
  이 파일은 공유 상수와 `Counter` 계정 타입을 가져옵니다. 명령어는 이러한
  정의를 사용하여 PDA를 도출하고, transfer 금액을 결정하며, 올바른 데이터 크기로
  계정을 할당합니다.

  **`derive(Accounts)`**

  `Initialize`는 `initialize` 명령어의 계정 컨텍스트입니다. 구조체의 각
  필드는 명령어가 호출될 때 포함되어야 하는 개별 계정을 나타냅니다. Anchor는
  핸들러가 실행되기 전에 이 구조체를 사용하여 들어오는 계정을 검증합니다.

  **`#[account(mut)]`**

  `#[account(mut)]`는 Anchor에게 payer 계정이 쓰기 가능해야 함을 알립니다.
  계정 생성과 transfer CPI 모두 payer로부터 lamport를 차감하기 때문에 이것이
  필요합니다.

  **`Signer<'info>`**

  `Signer<'info>`는 Anchor에게 payer가 트랜잭션에 서명해야 함을 알립니다.

  **`#[account(`**

  `#[account(...)]` 블록은 핸들러가 실행되기 전에 Anchor가 counter 계정을
  생성하고 검증하는 방법을 알려줍니다.

  **`init`**

  `init` 는 Anchor에게 핸들러가 실행되기 전에 `counter` 계정을 생성하도록
  지시합니다. 새 계정은 이 프로그램이 소유하므로 이 프로그램이 그 안에
  `Counter` 데이터를 저장할 수 있습니다.

  **`payer = payer`**

  `payer = payer` 는 새 카운터 계정 생성 비용을 지불할 `payer` 계정을
  지정합니다.

  **`space = 8 + Counter::INIT_SPACE`**

  `space = 8 + Counter::INIT_SPACE` 는 Anchor의 계정 판별자와 `state.rs` 의
  `Counter` 필드를 위한 바이트를 할당합니다. 판별자는 Anchor가 계정을 읽기
  전에 해당 계정이 예상된 타입을 저장하고 있는지 확인하는 데 도움을 줍니다.

  **`seeds = [COUNTER_SEED]`**

  `seeds = [COUNTER_SEED]` 는 카운터 계정 주소가 이 seed와 프로그램 ID로부터
  파생된 PDA여야 함을 나타냅니다. 하나의 고정 seed를 사용하면 이 프로그램에 대한
  카운터 PDA가 하나만 존재합니다. 실제 프로그램에서 별도의 카운터를 생성하려면
  일반적으로 사용자 주소와 같은 다른 seed를 추가해야 합니다.

  **`bump`**

  `bump` 는 Anchor에게 PDA bump를 찾아 검증하도록 지시합니다. bump는 파생된
  주소를 유효한 PDA로 만드는 추가 바이트입니다.

  **`Account<'info, Counter>`**

  `Account<'info, Counter>` 는 Anchor에게 계정 데이터를 `state.rs` 의
  `Counter` 타입으로 처리하도록 지시합니다. Anchor는 또한 해당 계정이 이
  프로그램에 의해 소유되어 있는지도 확인합니다.

  **`Program<'info, System>`**

  `Program<'info, System>` 는 호출자가 System Program을 제공할 것을
  요구합니다. Anchor는 `init` 계정 생성 제약 조건에 이를 사용합니다. 핸들러의
  전송 CPI 또한 System Program을 호출합니다.

  **`handle_initialize`**

  핸들러는 Anchor가 계정을 검증하고 카운터 계정을 생성한 후 실행되므로, 계정의
  초기 데이터를 안전하게 작성할 수 있습니다.

  **`counter.count = 0`**

  카운터 계정의 `count` 필드를 `0` 으로 설정합니다.

  **`counter.authority = ctx.accounts.payer.key()`**

  카운터 계정의 `authority` 필드를 지불자의 주소로 설정합니다.

  **`system_program::Transfer`**

  이 계정들은 System Program 전송 명령에 전달되는 계정들입니다. 이 전송 CPI는
  CPI가 다른 프로그램에 계정을 전달하는 방식을 보여주기 위한 예시로만
  포함되었습니다.

  **`CpiContext::new`**

  `CpiContext`는 Cross Program Invocation을 위한 대상 프로그램과 필요한
  계정들을 묶어줍니다. 컨텍스트를 생성하면 호출하려는 프로그램과 해당 프로그램이
  필요로 하는 계정들을 연결하여 CPI를 준비합니다.

  **`system_program::transfer`**

  이 CPI는 System Program의 전송 명령을 호출하여 `HELLO_WORLD_LAMPORTS`를
  지불자에서 카운터 계정으로 이동시킵니다.

  **`msg!`**

  `msg!`는 프로그램이 호출될 때 프로그램 로그에 메시지를 기록합니다.
</Note>

    ```rust initialize.rs focus={1-2}
        #[account(
    ```

### increment.rs

`increment.rs`는 기존 카운터 계정을 업데이트하는 데 필요한 계정들을 정의합니다.
핸들러는 서명자가 저장된 권한자인지 확인하고, 카운트가 지정된 `MAX_COUNT`에
도달하지 않았는지 검사한 후 카운트를 증가시킵니다.

```rust programs/my-program/src/instructions/increment.rs wrap
use anchor_lang::prelude::*;

use crate::{constants::*, error::ErrorCode, state::Counter};

#[derive(Accounts)]
pub struct Increment<'info> {
    #[account(
        mut,
        seeds = [COUNTER_SEED],
        bump
    )]
    pub counter: Account<'info, Counter>,
    pub authority: Signer<'info>,
}

pub fn handle_increment(ctx: Context<Increment>) -> Result<()> {
    require_keys_eq!(
        ctx.accounts.counter.authority,
        ctx.accounts.authority.key(),
        ErrorCode::Unauthorized,
    );
    require!(
        ctx.accounts.counter.count < MAX_COUNT,
        ErrorCode::CounterOverflow,
    );

    ctx.accounts.counter.count += 1;
    msg!("Hello, world! Counter is now {}", ctx.accounts.counter.count);
    Ok(())
}
```

<Note>
  **`derive(Accounts)`**

  `Increment`는 `increment` 명령의 계정 컨텍스트입니다. Anchor는 이를
  사용하여 변경 가능한 카운터 계정과 필요한 서명자를 검증합니다.

  **`mut`**

  `mut`는 Anchor에게 핸들러가 저장된 `count` 값을 업데이트하기 때문에
  카운터 계정이 쓰기 가능해야 한다고 알려줍니다.

  **`seeds = [COUNTER_SEED]`**

  `seeds = [COUNTER_SEED]`는 제공된 카운터 계정이 이 seed와 프로그램 ID로부터
  파생된 PDA인지 검증합니다.

  **`bump`**

  `bump`는 Anchor에게 카운터 계정의 PDA 범프를 찾아 검증하도록 지시합니다.

  **`Account<'info, Counter>`**

  `Account<'info, Counter>`는 Anchor에게 계정 데이터를 `state.rs`의
  `Counter` 타입으로 역직렬화하도록 지시합니다. 또한 Anchor는 해당 계정이 이
  프로그램에 의해 소유되어 있는지 확인합니다.

  **`Signer`**

  `Signer`는 권한자의 서명을 요구합니다. 그런 다음 핸들러는 이 서명자의 주소를
  카운터 계정에 저장된 권한자와 비교합니다.

  **`handle_increment`**

  핸들러는 Anchor가 계정 목록을 검증하고, 소유권을 확인하고, 카운터 계정을
  역직렬화한 후에 실행됩니다.

  **`require_keys_eq!`**

  `require_keys_eq!`는 두 개의 공개 키를 비교하여 서명자의 주소가 카운터
  계정에 저장된 권한자와 일치하지 않으면 명령어를 중단합니다. 이것이 이 템플릿의
  애플리케이션 수준 인가 규칙입니다.

  **`require!`**

  `require!`는 부울 규칙을 확인하고, 카운터가 이미 `MAX_COUNT`에 도달한
  경우 `CounterOverflow`와 함께 명령어를 중단합니다. 이 템플릿 규칙은 커스텀
  오류 처리와 변경 전 실패 처리를 보여줍니다.

  **`count += 1`**

  두 검사가 모두 통과된 후에만 핸들러가 카운터 계정 데이터를 업데이트합니다. 어느
  하나의 검사라도 실패하면 트랜잭션이 실패하고 계정은 변경되지 않습니다.

  **`msg!`**

  `msg!`는 프로그램이 호출될 때 프로그램 로그에 메시지를 기록합니다.
</Note>

  시작하지 않고도 컴파일된 프로그램을 등록하고, 계정을 생성하며, 트랜잭션을

  테스트는 `my_program::id()`를 통해 `declare_id!` 값에서 프로그램 주소를
  가져오고, 테스트 트랜잭션을 위한 새 payer keypair를 생성합니다.

  **`Pubkey::find_program_address`**

  카운터 주소는 프로그램이 사용하는 동일한 `COUNTER_SEED`에서 파생됩니다. 이를
  통해 테스트가 `initialize.rs`가 예상하는 PDA를 대상으로 합니다.

  **`include_bytes!`**

  `include_bytes!`는 빌드에서 생성된 컴파일된 `my_program.so` 파일을 읽습니다.
  해당 바이트는 LiteSVM이 테스트에서 실행할 실행 가능한 프로그램 코드입니다.

  **`svm.add_program`**

  `svm.add_program`는 컴파일된 프로그램 바이트를 LiteSVM의 프로그램 주소에
  등록합니다. 에어드롭을 통해 지불자는 트랜잭션 및 계정 생성에 필요한 충분한 로컬
  SOL을 받습니다.

  **`let instruction`**

  `Instruction::new_with_bytes`는 프로그램을 호출하는 명령을 생성합니다.
  여기에는 프로그램 ID, instruction data, 그리고 명령 계정이 포함됩니다.

  **`svm.latest_blockhash`**

  모든 Solana 트랜잭션에는 최근 블록해시가 필요합니다. 이 테스트에서 LiteSVM은
  트랜잭션에 사용할 블록해시를 제공합니다.

  **`Message::new_with_blockhash`**

  메시지에는 명령, 수수료 지불자, 블록해시가 포함됩니다. 이것이 서명될 트랜잭션
  데이터입니다.

  **`VersionedTransaction::try_new`**

  `VersionedTransaction::try_new`는 지불자 keypair로 메시지에 서명합니다.
  지불자는 트랜잭션 수수료를 지불하고 새 카운터 계정에 자금을 제공하기 때문에
  서명합니다.

  **`svm.send_transaction`**

  `svm.send_transaction`는 LiteSVM에서 트랜잭션을 실행합니다.

  **`svm.get_account`**

  트랜잭션이 실행된 후, 테스트는 계정 데이터를 검사하기 위해 LiteSVM에서 직접
  카운터 계정을 읽습니다.

  **`Counter::try_deserialize`**

  카운터 계정은 직렬화된 데이터를 저장합니다. `Counter::try_deserialize`는
  Anchor의 계정 판별자를 확인하고 계정 데이터를 `state.rs`의 `Counter`
  타입으로 다시 변환합니다.

  **`assert_eq!(counter_state.count, 0)`**

  `initialize`가 성공한 후, 테스트는 카운터 계정을 역직렬화하고 초기 상태가
  `handle_initialize`가 기록한 내용과 일치하는지 확인합니다.

  **`assert_eq!(counter_state.count, 1)`**

  `increment`가 성공한 후, 동일한 카운터 계정의 `count`가 `1`로
  설정되고 동일한 권한이 유지되어야 합니다.
</Note>

## 프로젝트 구성

루트 프로젝트 파일은 Anchor와 Cargo에게 프로그램을 빌드, 테스트 및 배포하는
방법을 알려줍니다. 전체 참조 문서는
[Anchor.toml 구성](https://www.anchor-lang.com/docs/references/anchor-toml) 및
[Anchor CLI](https://www.anchor-lang.com/docs/references/cli)에 대한 Anchor
문서를 참조하세요.

```toml Anchor.toml
skip_local_validator = true

[toolchain]

[features]
resolution = true
skip-lint = false

[programs.localnet]
my_program = "82sFkffP9wxwpyfZyeaKHH2chQoJPUGsJZSPi9mrUuXd"

[provider]
cluster = "localnet"
wallet = "~/.config/solana/id.json"

[scripts]
test = "cargo test"

[hooks]
```

<Note>
  **`skip_local_validator`**

  `skip_local_validator = true`는 Anchor에게 `anchor test`에 대해 validator를
  시작하지 않도록 지시합니다. Rust 테스트는 대신 LiteSVM을 사용합니다.

  **`programs.localnet`**

  `[programs.localnet]`는 Rust 크레이트 이름을 로컬 빌드 및 테스트에 사용되는
  프로그램 주소에 매핑합니다.

  **`provider`**

  `[provider]`는 `anchor deploy`와 같은 명령어에 사용할 기본 클러스터와 지갑을
  설정합니다.

  **`scripts`**

  `[scripts]`는 `anchor test`의 실행 내용을 변경합니다. 이 템플릿에서
  `anchor test`는 `cargo test`를 실행합니다.
</Note>
