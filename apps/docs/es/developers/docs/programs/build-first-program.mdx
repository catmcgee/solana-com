Este inicio rápido utiliza el proyecto base del
[framework Anchor](https://www.anchor-lang.com/docs) generado por `anchor init`.
Crearás el proyecto de forma local, ejecutarás sus pruebas, compilarás el
programa y revisarás el código del programa que Anchor genera.

## Requisitos previos

Antes de comenzar,
[instala las herramientas de desarrollo de Solana](/developers/docs/intro/installation). La
instalación incluye Rust, la CLI de Solana y la CLI de Anchor.

Usa la versión 1.1.2 o superior de la CLI de Anchor para esta plantilla.
Verifica tu versión instalada:

```bash Terminal
anchor --version
```

<Steps titleSize="h3">

<Step title="Crear el proyecto">

Ejecuta los siguientes comandos en tu terminal:

```bash Terminal
anchor init my-program
cd my-program
```

El proyecto base incluye un programa de Solana en `programs/my-program`. El
programa incluye dos instrucciones: una para inicializar una cuenta de contador
y otra para incrementar el contador.

Algunas partes de la plantilla demuestran patrones comunes de programas de
Solana: derivar direcciones de cuenta [PDA](/developers/docs/core/pda), realizar un Cross
Program Invocation ([CPI](/developers/docs/core/cpi)) para transferir SOL, y usar
verificaciones de error personalizadas para detener una instrucción cuando una
condición falla.

<Step title="Compilar el programa">

Ejecuta `anchor build` para compilar el programa base:

```bash Terminal
anchor build
```

El programa compilado se escribe en `target/deploy/my_program.so`. Cuando el
programa se despliega, el contenido de este archivo `.so` se almacena en una
cuenta onchain.

</Step>

<Step title="Ejecutar prueba">

Ejecuta la prueba predeterminada:

```bash Terminal
anchor test
```

El `Anchor.toml` de esta plantilla utiliza el comando de prueba de Rust:

```toml Anchor.toml
skip_local_validator = true

[scripts]
test = "cargo test"
```

La prueba carga el programa compilado en [LiteSVM](https://www.litesvm.com/),
crea un pagador, envía las instrucciones `initialize` y `increment`,
luego verifica el estado de la cuenta del contador.

Ejecutar `anchor test` también compila el programa, por lo que no es necesario
ejecutar `anchor build` primero al realizar pruebas localmente.

</Step>

<Step title="Desplegar programa">

Las pruebas locales son el ciclo de retroalimentación más rápido. Cuando estés
listo para desplegar en una red, por ejemplo devnet, primero compila y luego
despliega en un clúster.

Desplegar un programa de Solana requiere SOL porque el programa se almacena en
un program account, y dicha cuenta debe pagar por el espacio que utiliza. En
devnet, solicita SOL de devnet de forma gratuita desde el
[Solana Faucet](https://faucet.solana.com/) o con la CLI de Solana:

```bash Terminal
solana airdrop 2 --url devnet
```

```bash Terminal
anchor build
anchor deploy --provider.cluster devnet
```

</Step>

</Steps>

## Archivos fuente

El directorio `src` contiene el programa de Solana. La documentación de
[Estructura del programa](https://www.anchor-lang.com/docs/basics/program-structure)
de Anchor explica los macros principales utilizados aquí, incluyendo
`declare_id!`, `#[program]`, `#[derive(Accounts)]` y
`#[account]`. Esta sección recorre los archivos de la plantilla.

### lib.rs

`lib.rs` es el punto de entrada del programa. Conecta los archivos fuente,
define la dirección del programa y define las instrucciones del programa que los
usuarios pueden invocar.

```rust programs/my-program/src/lib.rs wrap
pub mod constants;
pub mod error;
pub mod instructions;
pub mod state;

use anchor_lang::prelude::*;

pub use constants::*;
pub use instructions::*;
pub use state::*;

declare_id!("82sFkffP9wxwpyfZyeaKHH2chQoJPUGsJZSPi9mrUuXd");

#[program]
pub mod my_program {
    use super::*;

    pub fn initialize(ctx: Context<Initialize>) -> Result<()> {
        crate::instructions::initialize::handle_initialize(ctx)
    }

    pub fn increment(ctx: Context<Increment>) -> Result<()> {
        crate::instructions::increment::handle_increment(ctx)
    }
}
```

<Note>
  **`pub mod constants`**

  `pub mod constants` incorpora `constants.rs` al crate del programa. Aquí es
  donde la plantilla almacena los valores compartidos del programa, como el seed
  del PDA, el monto de transferencia y el valor máximo del contador.

  **`pub mod error`**

  `pub mod error` incorpora `error.rs` al crate del programa. Este archivo
  define los errores personalizados que el programa puede devolver cuando una
  instrucción no es válida.

  **`pub mod instructions`**

  `pub mod instructions` incorpora `instructions.rs` al crate del programa.
  Ese archivo funciona como un índice para los archivos específicos de
  instrucciones en `src/instructions/`.

  **`pub mod state`**

  `pub mod state` incorpora `state.rs` al crate del programa. Este archivo
  define la estructura de datos para las cuentas propiedad de este programa,
  incluida la cuenta `Counter`.

  **`anchor_lang::prelude`**

  `anchor_lang::prelude::*` importa los tipos y macros de Anchor utilizados
  para definir un programa de Solana, incluyendo `Context`, `Result`,
  `Pubkey`, `Account`, `Signer` y los atributos de cuenta de Anchor.

  Las líneas `pub use` hacen que los elementos públicos de los módulos
  secundarios estén disponibles desde la raíz del crate. Esto mantiene los puntos
  de entrada de instrucciones concisos, como `Context<Initialize>` en lugar de
  una ruta de módulo más larga.

  **`declare_id!`**

  `declare_id!` define la dirección del programa. Debe coincidir con la
  dirección en `Anchor.toml`, el program account desplegado y cualquier usuario o
  prueba que llame al programa.

  **`#[program]`**

  `#[program]` le indica a Anchor que genere el punto de entrada del programa
  Solana y el código de despacho de instrucciones. Las funciones públicas de este
  módulo se convierten en las instrucciones que los usuarios pueden invocar.

  **`pub fn initialize`, `pub fn increment`**

  `initialize` y `increment` son los dos nombres de instrucciones que los
  usuarios pueden invocar. Cada una recibe un `Context<T>`. El tipo dentro de
  `Context` define las cuentas requeridas por esa instrucción, y Anchor valida
  dichas cuentas antes de que se ejecute la instrucción.

  **`handle_initialize`, `handle_increment`**

  La función manejadora contiene la lógica de la instrucción.
</Note>

### constants.rs

`constants.rs` centraliza los valores compartidos en un solo lugar. En esta
plantilla, `COUNTER_SEED` deriva el PDA del contador,
`HELLO_WORLD_LAMPORTS` se transfiere durante la inicialización, y
`MAX_COUNT` se verifica antes de incrementar.

```rust programs/my-program/src/constants.rs wrap
use anchor_lang::prelude::*;

#[constant]
pub const COUNTER_SEED: &[u8] = b"counter";

#[constant]
pub const HELLO_WORLD_LAMPORTS: u64 = 1;

#[constant]
pub const MAX_COUNT: u64 = 10;
```

<Note>
  **`#[constant]`**

  `#[constant]` indica a Anchor que incluya el valor en el IDL del programa.
  Esto hace que las constantes importantes del programa sean visibles para los
  clientes generados y las herramientas.

  **`COUNTER_SEED`**

  `COUNTER_SEED` es la cadena de bytes utilizada para derivar el PDA del
  contador. Tanto el programa como las pruebas usan este seed para que coincidan
  en la dirección de la cuenta sin necesidad de almacenar un keypair separado.
  Esta plantilla usa un seed fijo, por lo que el programa tiene una única
  dirección de contador. Los programas reales suelen incluir la dirección de un
  usuario u otro identificador en los seeds para crear múltiples cuentas
  relacionadas.

  **`HELLO_WORLD_LAMPORTS`**

  `HELLO_WORLD_LAMPORTS` es la cantidad de lamports transferidos desde el
  pagador a la cuenta del contador dentro de `initialize`. Es deliberadamente
  pequeña porque la plantilla demuestra un CPI al System Program.

  **`MAX_COUNT`**

  `MAX_COUNT` es el límite superior verificado por `increment`. Mantenerlo
  aquí proporciona al programa, las pruebas y el IDL generado un nombre compartido
  para esta regla.
</Note>

        #[account(

    }

  </div>

  <div>
    `initialize.rs` usa dos constantes:

    - `COUNTER_SEED` obtiene la dirección PDA del
      contador.
    - `HELLO_WORLD_LAMPORTS` establece la
      cantidad transferida desde el pagador a la cuenta del contador.
  </div>
</Columns>

### state.rs

`state.rs` define tipos de datos personalizados para las cuentas que el programa
crea y administra. El programa define instrucciones para crear, inicializar y
actualizar esos datos, pero los datos del contador no se almacenan dentro del
programa en sí. Se almacenan en una cuenta separada con su propia dirección.

```rust programs/my-program/src/state.rs wrap
use anchor_lang::prelude::*;

#[account]
#[derive(InitSpace)]
pub struct Counter {
    pub count: u64,
    pub authority: Pubkey,
}
```

<Note>
  **`#[account]`**

  `#[account]` le indica a Anchor que esta estructura es un dato que puede
  almacenarse en una cuenta onchain propiedad de este programa. Anchor la usa para
  serializar, deserializar y validar las cuentas `Counter`.

  **`InitSpace`**

  `InitSpace` permite a Anchor calcular `Counter::INIT_SPACE`, el número
  de bytes necesarios para los campos de esta estructura. El discriminador de
  cuenta de 8 bytes de Anchor se agrega por separado cuando se crea la cuenta.

  **`count`**

  `count` es el valor del contador almacenado dentro de los datos de la
  cuenta.

  **`authority`**

  `authority` almacena la dirección autorizada para incrementar el contador.
  `initialize` escribe esta dirección, y `increment` requiere que esa
  misma dirección firme.
</Note>

<Columns cols={2}>
  <div>
    ```rust initialize.rs highlight={4,12-13} wrap
    #[account(
        init,
        payer = payer,
        space = 8 + Counter::INIT_SPACE,
        seeds = [COUNTER_SEED],
        bump
    )]
    pub counter: Account<'info, Counter>,
    // ...

    pub fn handle_initialize(ctx: Context<Initialize>) -> Result<()> {
        ctx.accounts.counter.count = 0;
        ctx.accounts.counter.authority = ctx.accounts.payer.key();

        Ok(())
    }
    ```

    ```rust increment.rs highlight={4} wrap
    pub fn handle_increment(ctx: Context<Increment>) -> Result<()> {
        // ...

        ctx.accounts.counter.count += 1;
        Ok(())
    }
    ```
  </div>

  <div>
    `state.rs` define los datos de la cuenta `Counter`. Los archivos de
    instrucciones utilizan ese tipo cuando crean y actualizan la cuenta:

    - `Counter::INIT_SPACE` dimensiona la cuenta para
      los campos definidos en `state.rs`.
    - `count` y `authority` son los valores de
      los campos que se escriben cuando se inicializa la cuenta.
    - `count += 1` actualiza el valor del contador
      almacenado una vez que la validación es exitosa.
  </div>
</Columns>

### error.rs

`error.rs` define los errores personalizados del programa. En esta plantilla,
los errores demuestran cómo los manejadores de instrucciones se detienen cuando
un llamante no tiene permiso para actualizar el contador o cuando el contador ya
ha alcanzado `MAX_COUNT`.

```rust programs/my-program/src/error.rs wrap
use anchor_lang::prelude::*;

#[error_code]
pub enum ErrorCode {
    #[msg("Only the counter authority can update this counter")]
    Unauthorized,
    #[msg("Counter has reached the maximum value")]
    CounterOverflow,
}
```

<Note>
  **`#[error_code]`**

  `#[error_code]` indica a Anchor que convierta estas variantes en errores de
  programa personalizados. Los clientes y las pruebas pueden usar esos errores en
  lugar de adivinar a partir de códigos de error sin procesar.

  **`Unauthorized`**

  `Unauthorized` se devuelve cuando el firmante de la transacción no es la
  autoridad almacenada en la cuenta del contador.

  **`CounterOverflow`**

  `CounterOverflow` se devuelve cuando al incrementar se infringiría la regla
  `MAX_COUNT` del programa.
</Note>

<Columns cols={2}>
  <div>
    ```rust increment.rs highlight={5,9} wrap
    pub fn handle_increment(ctx: Context<Increment>) -> Result<()> {
        require_keys_eq!(
            ctx.accounts.counter.authority,
            ctx.accounts.authority.key(),
            ErrorCode::Unauthorized,
        );
        require!(
            ctx.accounts.counter.count < MAX_COUNT,
            ErrorCode::CounterOverflow,
        );

        ctx.accounts.counter.count += 1;
        msg!("Hello, world! Counter is now {}", ctx.accounts.counter.count);
        Ok(())
    }
    ```
  </div>

  <div>
    `error.rs` nombra los errores que la instrucción puede devolver:

    - `ErrorCode::Unauthorized` se devuelve cuando
      el firmante no es la autoridad almacenada en la cuenta del contador.
    - `ErrorCode::CounterOverflow` se devuelve cuando
      el contador ya ha alcanzado `MAX_COUNT`.
  </div>
</Columns>

### instructions.rs

`instructions.rs` conecta los archivos de instrucciones con el crate del
programa para que `lib.rs` pueda acceder al código de instrucciones
`initialize` y `increment`. Cada archivo de instrucciones define las
cuentas requeridas por esa instrucción y la lógica del manejador que se ejecuta
después de que Anchor valida dichas cuentas.

```rust programs/my-program/src/instructions.rs wrap
pub mod initialize;
pub mod increment;

pub use initialize::*;
pub use increment::*;
```

<Note>
  **`pub mod initialize`**

  Las líneas `pub mod` hacen que `src/instructions/initialize.rs` e
  `src/instructions/increment.rs` formen parte del crate del programa.

  **`pub use initialize`**

  Las líneas `pub use` reexportan elementos públicos de esos archivos. Esto
  hace que las estructuras de cuentas de instrucciones y las funciones manejadoras
  estén disponibles a través del módulo `instructions`.
</Note>

### initialize.rs

`initialize.rs` define las cuentas necesarias para crear la cuenta del contador
y luego escribe los valores iniciales de la cuenta. La estructura
`#[derive(Accounts)]` utiliza las
[restricciones de cuenta](https://www.anchor-lang.com/docs/references/account-constraints)
de Anchor para especificar qué cuentas son requeridas y cómo se crea la nueva
cuenta del contador.

```rust programs/my-program/src/instructions/initialize.rs wrap
use anchor_lang::prelude::*;

use crate::{constants::*, state::Counter};

#[derive(Accounts)]
pub struct Initialize<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,
    #[account(
        init,
        payer = payer,
        space = 8 + Counter::INIT_SPACE,
        seeds = [COUNTER_SEED],
        bump
    )]
    pub counter: Account<'info, Counter>,
    pub system_program: Program<'info, System>,
}

pub fn handle_initialize(ctx: Context<Initialize>) -> Result<()> {
    ctx.accounts.counter.count = 0;
    ctx.accounts.counter.authority = ctx.accounts.payer.key();

    let cpi_accounts = anchor_lang::system_program::Transfer {
        from: ctx.accounts.payer.to_account_info(),
        to: ctx.accounts.counter.to_account_info(),
    };
    let cpi_ctx = CpiContext::new(anchor_lang::system_program::ID, cpi_accounts);
    anchor_lang::system_program::transfer(cpi_ctx, HELLO_WORLD_LAMPORTS)?;

    msg!("Hello, world! Counter initialized");
    Ok(())
}
```

<Note>
  Este archivo importa las constantes compartidas y el tipo de cuenta
  `Counter`. La instrucción usa esas definiciones para derivar el PDA, elegir
  el monto de transferencia y asignar la cuenta con el tamaño de datos correcto.

  **`derive(Accounts)`**

  `Initialize` es el contexto de cuentas para la instrucción `initialize`.
  Cada campo en la estructura representa una cuenta separada que debe incluirse
  cuando se llama a la instrucción. Anchor usa la estructura para validar esas
  cuentas entrantes antes de que se ejecute el handler.

  **`#[account(mut)]`**

  `#[account(mut)]` le indica a Anchor que la cuenta del pagador debe ser
  modificable. Esto es necesario porque tanto la creación de la cuenta como el CPI
  de transferencia deducen lamports del pagador.

  **`Signer<'info>`**

  `Signer<'info>` le indica a Anchor que el pagador debe firmar la
  transacción.

  **`#[account(`**

  El bloque `#[account(...)]` le indica a Anchor cómo crear y validar la
  cuenta del contador antes de que se ejecute el handler.

  **`init`**

  `init` le indica a Anchor que cree la cuenta `counter` antes de que se
  ejecute el handler. La nueva cuenta es propiedad de este programa, por lo que
  este programa puede almacenar datos de `Counter` en ella.

  **`payer = payer`**

  `payer = payer` especifica la cuenta `payer` como pagadora de la
  creación de la nueva cuenta del contador.

  **`space = 8 + Counter::INIT_SPACE`**

  `space = 8 + Counter::INIT_SPACE` reserva bytes para el discriminador de
  cuenta de Anchor más los campos `Counter` de `state.rs`. El discriminador
  ayuda a Anchor a confirmar que la cuenta almacena el tipo esperado antes de
  leerla.

  **`seeds = [COUNTER_SEED]`**

  `seeds = [COUNTER_SEED]` indica que la dirección de la cuenta del contador
  debe ser el PDA derivado de este seed y el ID del programa. Con un seed fijo,
  hay un único PDA del contador para este programa. Para crear contadores
  separados en un programa real, normalmente se añadiría otro seed, como la
  dirección de un usuario.

  **`bump`**

  `bump` le indica a Anchor que encuentre y valide el bump del PDA, que es el
  byte adicional que hace que la dirección derivada sea válida como PDA.

  **`Account<'info, Counter>`**

  `Account<'info, Counter>` le indica a Anchor que trate los datos de la
  cuenta como el tipo `Counter` de `state.rs`. Anchor también verifica que la
  cuenta sea propiedad de este programa.

  **`Program<'info, System>`**

  `Program<'info, System>` requiere que el emisor proporcione el System
  Program. Anchor lo utiliza para la restricción de creación de cuenta `init`.
  El CPI de transferencia del handler también invoca el System Program.

  **`handle_initialize`**

  El handler se ejecuta después de que Anchor valide las cuentas y cree la cuenta
  del contador, por lo que puede escribir de forma segura los datos iniciales de
  la cuenta.

  **`counter.count = 0`**

  Establece el campo `count` en la cuenta del contador a `0`.

  **`counter.authority = ctx.accounts.payer.key()`**

  Establece el campo `authority` en la cuenta del contador con la dirección
  del pagador.

  **`system_program::Transfer`**

  Estas son las cuentas que se pasan a la instrucción de transferencia de System
  Program. Esta CPI de transferencia se incluye únicamente para demostrar cómo una
  CPI pasa cuentas a otro programa.

  **`CpiContext::new`**

  `CpiContext` empaqueta el programa de destino y las cuentas requeridas para
  una Cross Program Invocation. Crear el contexto prepara la CPI al vincular el
  programa que deseas llamar con las cuentas que ese programa espera.

  **`system_program::transfer`**

  Esta CPI invoca la instrucción de transferencia de System Program y mueve
  `HELLO_WORLD_LAMPORTS` del pagador a la cuenta del contador.

  **`msg!`**

  `msg!` escribe un mensaje en los registros del programa cuando este es
  invocado.
</Note>

### increment.rs

`increment.rs` define las cuentas necesarias para actualizar una cuenta de
contador existente. El manejador verifica que el firmante sea la autoridad
almacenada, comprueba que el conteo no haya alcanzado el `MAX_COUNT`
especificado y luego incrementa el conteo.

```rust programs/my-program/src/instructions/increment.rs wrap
use anchor_lang::prelude::*;

use crate::{constants::*, error::ErrorCode, state::Counter};

#[derive(Accounts)]
pub struct Increment<'info> {
    #[account(
        mut,
        seeds = [COUNTER_SEED],
        bump
    )]
    pub counter: Account<'info, Counter>,
    pub authority: Signer<'info>,
}

pub fn handle_increment(ctx: Context<Increment>) -> Result<()> {
    require_keys_eq!(
        ctx.accounts.counter.authority,
        ctx.accounts.authority.key(),
        ErrorCode::Unauthorized,
    );
    require!(
        ctx.accounts.counter.count < MAX_COUNT,
        ErrorCode::CounterOverflow,
    );

    ctx.accounts.counter.count += 1;
    msg!("Hello, world! Counter is now {}", ctx.accounts.counter.count);
    Ok(())
}
```

<Note>
  **`derive(Accounts)`**

  `Increment` es el contexto de cuenta para la instrucción `increment`.
  Anchor lo utiliza para validar la cuenta de contador mutable y el firmante
  requerido.

  **`mut`**

  `mut` le indica a Anchor que la cuenta del contador debe ser escribible
  porque el handler actualiza el valor `count` almacenado.

  **`seeds = [COUNTER_SEED]`**

  `seeds = [COUNTER_SEED]` verifica que la cuenta del contador proporcionada
  sea el PDA derivado de este seed y el ID del programa.

  **`bump`**

  `bump` le indica a Anchor que encuentre y valide el bump del PDA para la
  cuenta del contador.

  **`Account<'info, Counter>`**

  `Account<'info, Counter>` le indica a Anchor que deserialice los datos de la
  cuenta como el tipo `Counter` de `state.rs`. Anchor también verifica que la
  cuenta sea propiedad de este programa.

  **`Signer`**

  `Signer` requiere la firma de la autoridad. El handler luego compara la
  dirección de este firmante con la autoridad almacenada en la cuenta del
  contador.

  **`handle_increment`**

  El handler se ejecuta después de que Anchor valida la lista de cuentas, verifica
  la propiedad y deserializa la cuenta del contador.

  **`require_keys_eq!`**

  `require_keys_eq!` compara dos claves públicas y detiene la instrucción a
  menos de que la dirección del firmante coincida con la autoridad almacenada en
  la cuenta del contador. Esta es la regla de autorización a nivel de aplicación
  de la plantilla.

  **`require!`**

  `require!` comprueba una regla booleana y detiene la instrucción con
  `CounterOverflow` si el contador ya ha alcanzado `MAX_COUNT`. Esta regla
  de plantilla demuestra el uso de errores personalizados y el fallo antes de la
  mutación.

  **`count += 1`**

  Solo después de que ambas verificaciones pasen, el handler actualiza los datos
  de la cuenta del contador. Si cualquiera de las verificaciones falla, la
  transacción falla y la cuenta no se modifica.

  **`msg!`**

  `msg!` escribe un mensaje en los registros del programa cuando este es
  invocado.
</Note>

    instrucción `increment`. La prueba pasa esas mismas cuentas al helper
    generado `my_program::accounts::Increment`:

    - `counter` se pasa como `counter`.
    - `authority` se pasa como
      `authority: payer.pubkey()`.

    `my_program::instruction::Increment {}.data()`
    crea el instruction data. Aquí es donde se codificarían los argumentos de
    instrucción, pero esta instrucción `increment` no requiere ningún argumento.
  </div>
</Columns>

```rust programs/my-program/tests/test_initialize.rs wrap
use {
    anchor_lang::{
        prelude::Pubkey,
        solana_program::{instruction::Instruction, system_program},
        AccountDeserialize, InstructionData, ToAccountMetas,
    },
    litesvm::LiteSVM,
    solana_keypair::Keypair,
    solana_message::{Message, VersionedMessage},
    solana_signer::Signer,
    solana_transaction::versioned::VersionedTransaction,
};

#[test]
fn test_initialize() {
    let program_id = my_program::id();
    let payer = Keypair::new();
    let counter = Pubkey::find_program_address(
        &[my_program::constants::COUNTER_SEED],
        &program_id,
    )
    .0;
    let mut svm = LiteSVM::new();
    let bytes = include_bytes!(concat!(
        env!("CARGO_TARGET_TMPDIR"),
        "/../deploy/my_program.so"
    ));
    svm.add_program(program_id, bytes).unwrap();
    svm.airdrop(&payer.pubkey(), 1_000_000_000).unwrap();

    let instruction = Instruction::new_with_bytes(
        program_id,
        &my_program::instruction::Initialize {}.data(),
        my_program::accounts::Initialize {
            payer: payer.pubkey(),
            counter,
            system_program: system_program::ID,
        }
        .to_account_metas(None),
    );

    let blockhash = svm.latest_blockhash();
    let msg = Message::new_with_blockhash(&[instruction], Some(&payer.pubkey()), &blockhash);
    let tx = VersionedTransaction::try_new(VersionedMessage::Legacy(msg), &[&payer]).unwrap();

    let res = svm.send_transaction(tx);
    assert!(res.is_ok());

    let counter_account = svm.get_account(&counter).unwrap();
    let mut data: &[u8] = &counter_account.data;
    let counter_state = my_program::state::Counter::try_deserialize(&mut data).unwrap();
    assert_eq!(counter_state.count, 0);
    assert_eq!(counter_state.authority, payer.pubkey());

    let instruction = Instruction::new_with_bytes(
        program_id,
        &my_program::instruction::Increment {}.data(),
        my_program::accounts::Increment {
            counter,
            authority: payer.pubkey(),
        }
        .to_account_metas(None),
    );

    let blockhash = svm.latest_blockhash();
    let msg = Message::new_with_blockhash(&[instruction], Some(&payer.pubkey()), &blockhash);
    let tx = VersionedTransaction::try_new(VersionedMessage::Legacy(msg), &[&payer]).unwrap();

    let res = svm.send_transaction(tx);
    assert!(res.is_ok());

    let counter_account = svm.get_account(&counter).unwrap();
    let mut data: &[u8] = &counter_account.data;
    let counter_state = my_program::state::Counter::try_deserialize(&mut data).unwrap();
    assert_eq!(counter_state.count, 1);
    assert_eq!(counter_state.authority, payer.pubkey());
}
```

<Note>
  **`litesvm::LiteSVM`**

  `LiteSVM` es una VM de Solana en proceso para pruebas. Permite que la prueba
  registre el programa compilado, cree cuentas, envíe transacciones e inspeccione
  el estado de las cuentas sin necesidad de iniciar un proceso de validator.

  **`let program_id`**

  La prueba obtiene la dirección del programa a partir del valor `declare_id!`
  mediante `my_program::id()` y crea un nuevo keypair de pagador para la
  transacción de prueba.

  **`Pubkey::find_program_address`**

  La dirección del contador se deriva del mismo `COUNTER_SEED` utilizado por
  el programa. Esto hace que la prueba apunte al PDA que `initialize.rs` espera.

  **`include_bytes!`**

  `include_bytes!` lee el archivo `my_program.so` compilado generado por la
  construcción. Esos bytes son el código ejecutable del programa que LiteSVM
  ejecutará en la prueba.

  **`svm.add_program`**

  `svm.add_program` registra los bytes del programa compilado en la dirección
  del programa en LiteSVM. El airdrop le otorga al pagador suficiente SOL local
  para pagar la transacción y la creación de la cuenta.

  **`let instruction`**

  `Instruction::new_with_bytes` crea una instrucción para invocar el programa.
  Incluye el ID del programa, instruction data y las cuentas de la instrucción.

  **`svm.latest_blockhash`**

  Cada transacción de Solana necesita un blockhash reciente. En esta prueba,
  LiteSVM proporciona un blockhash para usar en la transacción.

  **`Message::new_with_blockhash`**

  El mensaje contiene la instrucción, el pagador de comisiones y el blockhash.
  Estos son los datos de la transacción que serán firmados.

  **`VersionedTransaction::try_new`**

  `VersionedTransaction::try_new` firma el mensaje con el keypair del pagador.
  El pagador firma porque paga la comisión de la transacción y financia la nueva
  cuenta del contador.

  **`svm.send_transaction`**

  `svm.send_transaction` ejecuta la transacción en LiteSVM.

  **`svm.get_account`**

  Después de que se ejecuta la transacción, la prueba lee la cuenta del contador
  directamente desde LiteSVM para poder inspeccionar los datos de la cuenta.

  **`Counter::try_deserialize`**

  La cuenta del contador almacena datos serializados.
  `Counter::try_deserialize` verifica el discriminador de cuenta de Anchor y
  convierte los datos de la cuenta de vuelta al tipo `Counter` desde
  `state.rs`.

  **`assert_eq!(counter_state.count, 0)`**

  Después de que `initialize` se ejecuta correctamente, la prueba deserializa
  la cuenta del contador y verifica que el estado inicial coincida con lo que
  `handle_initialize` escribió.

  **`assert_eq!(counter_state.count, 1)`**

  Después de que `increment` se ejecuta correctamente, la misma cuenta del
  contador debería tener `count` establecido en `1` manteniendo la misma
  autoridad.
</Note>

<Note>
  **`skip_local_validator`**

  `skip_local_validator = true` le indica a Anchor que no inicie un validator para
  `anchor test`. La prueba de Rust usa LiteSVM en su lugar.

  **`programs.localnet`**

  `[programs.localnet]` asigna el nombre del crate de Rust a la dirección del
  programa utilizada en builds y pruebas locales.

  **`provider`**

  `[provider]` establece el clúster y la billetera predeterminados para comandos
  como `anchor deploy`.

  **`scripts`**

  `[scripts]` cambia lo que ejecuta `anchor test`. En esta plantilla,
  `anchor test` ejecuta`cargo test`.
</Note>
