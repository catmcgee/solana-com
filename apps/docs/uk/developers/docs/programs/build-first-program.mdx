Цей швидкий старт використовує стартовий проєкт
[фреймворку Anchor](https://www.anchor-lang.com/docs), згенерований командою
`anchor init`. Ви створите проєкт локально, запустите його тести, зберете
програму та ознайомитеся з кодом програми, який генерує Anchor.

## Передумови

Перш ніж почати,
[встановіть інструменти розробки Solana](/developers/docs/quickstart). До
встановлення входять Rust, Solana CLI та Anchor CLI.

Для цього шаблону використовуйте Anchor CLI версії 1.1.2 або вище. Перевірте
встановлену версію:

```bash Terminal
anchor --version
```

<Steps titleSize="h3">

<Step title="Створення проєкту">

Виконайте наступні команди у вашому терміналі:

```bash Terminal
anchor init my-program
cd my-program
```

Стартовий проєкт містить одну програму Solana у `programs/my-program`. Програма
включає дві інструкції: одну для ініціалізації облікового запису лічильника та
одну для збільшення лічильника.

Деякі частини шаблону демонструють типові патерни програм Solana: виведення
адрес облікових записів [PDA](/developers/docs/core/pda), виконання Cross Program
Invocation ([CPI](/developers/docs/core/cpi)) для переказу SOL, а також використання
власних перевірок помилок для зупинки інструкції у разі невиконання умови.

</Step>

<Step title="Збірка програми">

Запустіть `anchor build` для компіляції стартової програми:

```bash Terminal
anchor build
```

Скомпільовану програму записано до `target/deploy/my_program.so`. Під час
розгортання програми вміст цього файлу `.so` зберігається в обліковому записі в
мережі.

</Step>

<Step title="Запустити тест">

Запустіть стандартний тест:

```bash Terminal
anchor test
```

`Anchor.toml` цього шаблону використовує команду тестування Rust:

```toml Anchor.toml
skip_local_validator = true

[scripts]
test = "cargo test"
```

Тест завантажує скомпільовану програму в [LiteSVM](https://www.litesvm.com/),
створює платника, надсилає інструкції `initialize` та `increment`, а
потім перевіряє стан рахунку лічильника.

Запуск `anchor test` також компілює програму, тому вам не потрібно запускати
`anchor build` спочатку під час локального тестування.

</Step>

<Step title="Розгортання програми">

Локальні тести — це найшвидший цикл зворотного зв'язку. Коли ви готові до
розгортання в мережі, наприклад devnet, спочатку виконайте збірку, а потім
розгорніть у кластері.

Розгортання програми Solana вимагає SOL, оскільки програма зберігається в
акаунті, і акаунт повинен оплачувати використовуваний простір. У devnet
запросіть безкоштовний devnet SOL із [Solana Faucet](https://faucet.solana.com/)
або за допомогою Solana CLI:

```bash Terminal
solana airdrop 2 --url devnet
```

```bash Terminal
anchor build
anchor deploy --provider.cluster devnet
```

</Step>

</Steps>

## Вихідні файли

Директорія `src` містить програму Solana. Документація Anchor щодо
[структури програми](https://www.anchor-lang.com/docs/basics/program-structure)
пояснює основні макроси, що використовуються тут, зокрема `declare_id!`,
`#[program]`, `#[derive(Accounts)]` та `#[account]`. У цьому розділі
розглядаються файли шаблону.

### lib.rs

`lib.rs` — це точка входу програми. Вона з'єднує вихідні файли, визначає адресу
програми та визначає інструкції програми, які можуть викликати користувачі.

```rust programs/my-program/src/lib.rs wrap
pub mod constants;
pub mod error;
pub mod instructions;
pub mod state;

use anchor_lang::prelude::*;

pub use constants::*;
pub use instructions::*;
pub use state::*;

declare_id!("82sFkffP9wxwpyfZyeaKHH2chQoJPUGsJZSPi9mrUuXd");

#[program]
pub mod my_program {
    use super::*;

    pub fn initialize(ctx: Context<Initialize>) -> Result<()> {
        crate::instructions::initialize::handle_initialize(ctx)
    }

    pub fn increment(ctx: Context<Increment>) -> Result<()> {
        crate::instructions::increment::handle_increment(ctx)
    }
}
```

<Note>
  **`pub mod constants`**

  `pub mod constants` додає `constants.rs` до крейта програми. Тут шаблон
  зберігає спільні значення програми, такі як seed PDA, сума переказу та
  максимальне значення лічильника.

  **`pub mod error`**

  `pub mod error` додає `error.rs` до крейта програми. Цей файл визначає
  користувацькі помилки, які програма може повертати, коли інструкція є недійсною.

  **`pub mod instructions`**

  `pub mod instructions` додає `instructions.rs` до крейта програми. Цей файл
  працює як індекс для файлів, що стосуються конкретних інструкцій, у
  `src/instructions/`.

  **`pub mod state`**

  `pub mod state` додає `state.rs` до крейта програми. Цей файл визначає
  структуру даних для акаунтів, якими володіє ця програма, включаючи акаунт
  `Counter`.

  **`anchor_lang::prelude`**

  `anchor_lang::prelude::*` імпортує типи та макроси Anchor, що
  використовуються для визначення програми Solana, включаючи `Context`,
  `Result`, `Pubkey`, `Account`, `Signer` та атрибути акаунтів
  Anchor.

  Рядки `pub use` роблять публічні елементи дочірніх модулів доступними з
  кореня крейта. Це дозволяє скорочувати точки входу інструкцій, наприклад
  `Context<Initialize>` замість довшого шляху до модуля.

  **`declare_id!`**

  `declare_id!` визначає адресу програми. Вона має збігатися з адресою у
  `Anchor.toml`, розгорнутому program account та у будь-яких користувачів або
  тестів, що викликають програму.

  **`#[program]`**

  `#[program]` вказує Anchor згенерувати точку входу програми Solana та код
  диспетчеризації інструкцій. Публічні функції у цьому модулі стають інструкціями,
  які можуть викликати користувачі.

  **`pub fn initialize`, `pub fn increment`**

  `initialize` та `increment` — це дві назви інструкцій, які можуть
  викликати користувачі. Кожна отримує `Context<T>`. Тип у `Context`
  визначає акаунти, необхідні для цієї інструкції, і Anchor перевіряє ці акаунти
  перед виконанням інструкції.

  **`handle_initialize`, `handle_increment`**

  Функція-обробник містить логіку для інструкції.
</Note>

кластері. `declare_id!` визначає адресу програми в самій програмі для
перевірок безпеки.

### constants.rs

`constants.rs` зберігає спільні значення в одному місці. У цьому шаблоні
`COUNTER_SEED` використовується для виведення PDA лічильника,
`HELLO_WORLD_LAMPORTS` передається під час ініціалізації, а `MAX_COUNT`
перевіряється перед інкрементуванням.

```rust programs/my-program/src/constants.rs wrap
use anchor_lang::prelude::*;

#[constant]
pub const COUNTER_SEED: &[u8] = b"counter";

#[constant]
pub const HELLO_WORLD_LAMPORTS: u64 = 1;

#[constant]
pub const MAX_COUNT: u64 = 10;
```

<Note>
  **`#[constant]`**

  `#[constant]` вказує Anchor включити значення до IDL програми. Це робить
  важливі константи програми видимими для згенерованих клієнтів та інструментів.

  **`COUNTER_SEED`**

  `COUNTER_SEED` — це рядок байтів, який використовується для виведення PDA
  лічильника. Програма та тест обидва використовують цей seed, тому вони
  погоджуються щодо адреси акаунта без збереження окремого keypair. Цей шаблон
  використовує один фіксований seed, тому програма має одну адресу лічильника.
  Реальні програми часто включають адресу користувача або інший ідентифікатор у
  seeds для створення багатьох пов'язаних акаунтів.

  **`HELLO_WORLD_LAMPORTS`**

  `HELLO_WORLD_LAMPORTS` — це кількість lamport, що передається від платника
  до акаунта лічильника всередині `initialize`. Вона навмисно мала, оскільки
  шаблон демонструє CPI до System Program.

  **`MAX_COUNT`**

  `MAX_COUNT` — це верхня межа, яку перевіряє `increment`. Зберігання її
  тут надає програмі, тестам та згенерованому IDL одну спільну назву для цього
  правила.
</Note>

### state.rs

`state.rs` визначає власні типи даних для акаунтів, які програма створює та
якими керує. Програма визначає інструкції для створення, ініціалізації та
оновлення цих даних, але дані лічильника зберігаються не всередині самої
програми. Вони зберігаються в окремому акаунті з власною адресою.

```rust programs/my-program/src/state.rs wrap
use anchor_lang::prelude::*;

#[account]
#[derive(InitSpace)]
pub struct Counter {
    pub count: u64,
    pub authority: Pubkey,
}
```

<Note>
  **`#[account]`**

  `#[account]` повідомляє Anchor, що ця структура є даними, які можуть
  зберігатися в onchain-акаунті, яким керує ця програма. Anchor використовує її
  для серіалізації, десеріалізації та перевірки акаунтів `Counter`.

  **`InitSpace`**

  `InitSpace` дозволяє Anchor обчислити `Counter::INIT_SPACE` — кількість
  байтів, необхідних для полів цієї структури. 8-байтовий дискримінатор акаунту
  Anchor додається окремо під час створення акаунту.

  **`count`**

  `count` — це значення лічильника, що зберігається всередині даних акаунту.

  **`authority`**

  `authority` зберігає адресу, якій дозволено збільшувати лічильник.
  `initialize` записує цю адресу, а `increment` вимагає підпису з тієї
  самої адреси.
</Note>

    `state.rs` визначає дані акаунта `Counter`. Файли інструкцій використовують
    цей тип під час створення та оновлення акаунта:

    - `Counter::INIT_SPACE` визначає розмір акаунта для
      полів, описаних у `state.rs`.
    - `count` та `authority` — це значення
      полів, що записуються під час ініціалізації акаунта.
    - `count += 1` оновлює збережене значення

### error.rs

`error.rs` визначає власні помилки програми. У цьому шаблоні помилки
демонструють, як обробники інструкцій зупиняються, якщо виклик не має права
оновлювати лічильник або лічильник вже досяг `MAX_COUNT`.

```rust programs/my-program/src/error.rs wrap
use anchor_lang::prelude::*;

#[error_code]
pub enum ErrorCode {
    #[msg("Only the counter authority can update this counter")]
    Unauthorized,
    #[msg("Counter has reached the maximum value")]
    CounterOverflow,
}
```

<Note>
  **`#[error_code]`**

  `#[error_code]` вказує Anchor перетворити ці варіанти на власні помилки
  програми. Клієнти та тести можуть використовувати ці помилки замість того, щоб
  здогадуватися за необробленими кодами помилок.

  **`Unauthorized`**

  `Unauthorized` повертається, коли підписант транзакції не є authority,
  збереженим в акаунті лічильника.

  **`CounterOverflow`**

  `CounterOverflow` повертається, коли інкремент порушить правило
  `MAX_COUNT` програми.
</Note>

<Columns cols={2}>
  <div>
    ```rust increment.rs highlight={5,9} wrap
    pub fn handle_increment(ctx: Context<Increment>) -> Result<()> {
        require_keys_eq!(
            ctx.accounts.counter.authority,
            ctx.accounts.authority.key(),
            ErrorCode::Unauthorized,

        require!(
            ctx.accounts.counter.count < MAX_COUNT,

        );

        ctx.accounts.counter.count += 1;
        msg!("Hello, world! Counter is now {}", ctx.accounts.counter.count);
        Ok(())
    }
    ```
  </div>

  <div>
    `error.rs` називає помилки, які може повернути інструкція:

    - `ErrorCode::Unauthorized` повертається, коли
      підписант не є authority, збереженим в акаунті лічильника.
    - `ErrorCode::CounterOverflow` повертається, коли
      лічильник вже досяг `MAX_COUNT`.
  </div>
</Columns>

### instructions.rs

`instructions.rs` підключає файли інструкцій до крейту програми, щоб `lib.rs`
міг отримати доступ до коду інструкцій `initialize` та `increment`.
Кожен файл інструкції визначає облікові записи, необхідні для цієї інструкції,
та логіку обробника, яка виконується після того, як Anchor перевірить ці
облікові записи.

```rust programs/my-program/src/instructions.rs wrap
pub mod initialize;
pub mod increment;

pub use initialize::*;
pub use increment::*;
```

<Note>
  **`pub mod initialize`**

  Рядки `pub mod` роблять `src/instructions/initialize.rs` та
  `src/instructions/increment.rs` частиною крейту програми.

  **`pub use initialize`**

  Рядки `pub use` повторно експортують публічні елементи з цих файлів. Це
  робить структури облікових записів інструкцій та функції обробників доступними
  через модуль `instructions`.
</Note>

### initialize.rs

`initialize.rs` визначає облікові записи, необхідні для створення облікового
запису лічильника, а потім записує його початкові значення. Структура
`#[derive(Accounts)]` використовує
[обмеження облікових записів](https://www.anchor-lang.com/docs/references/account-constraints)
Anchor, щоб вказати, які облікові записи є обов'язковими та як створюється новий
обліковий запис лічильника.

```rust programs/my-program/src/instructions/initialize.rs wrap
use anchor_lang::prelude::*;

use crate::{constants::*, state::Counter};

#[derive(Accounts)]
pub struct Initialize<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,
    #[account(
        init,
        payer = payer,
        space = 8 + Counter::INIT_SPACE,
        seeds = [COUNTER_SEED],
        bump
    )]
    pub counter: Account<'info, Counter>,
    pub system_program: Program<'info, System>,
}

pub fn handle_initialize(ctx: Context<Initialize>) -> Result<()> {
    ctx.accounts.counter.count = 0;
    ctx.accounts.counter.authority = ctx.accounts.payer.key();

    let cpi_accounts = anchor_lang::system_program::Transfer {
        from: ctx.accounts.payer.to_account_info(),
        to: ctx.accounts.counter.to_account_info(),
    };
    let cpi_ctx = CpiContext::new(anchor_lang::system_program::ID, cpi_accounts);
```

<Note>
  Цей файл імпортує спільні константи та тип акаунту `Counter`. Інструкція
  використовує ці визначення для виведення PDA, вибору суми переказу та виділення
  акаунту з правильним розміром даних.

  **`derive(Accounts)`**

  `Initialize` — це контекст акаунтів для інструкції `initialize`. Кожне
  поле у структурі представляє окремий акаунт, який має бути включений під час
  виклику інструкції. Anchor використовує структуру для перевірки вхідних акаунтів
  перед запуском обробника.

  **`#[account(mut)]`**

  `#[account(mut)]` повідомляє Anchor, що акаунт платника повинен бути
  доступний для запису. Це необхідно, оскільки створення акаунту та CPI переказу
  обидва знімають lamport з платника.

  **`Signer<'info>`**

  `Signer<'info>` повідомляє Anchor, що платник повинен підписати транзакцію.

  **`#[account(`**

  Блок `#[account(...)]` повідомляє Anchor, як створити та перевірити акаунт
  лічильника перед запуском обробника.

  **`init`**

  `init` вказує Anchor створити акаунт `counter` до виконання обробника.
  Новий акаунт належить цій програмі, тому вона може зберігати в ньому дані
  `Counter`.

  **`payer = payer`**

  `payer = payer` вказує акаунт `payer` як платника за створення нового
  акаунта лічильника.

  **`space = 8 + Counter::INIT_SPACE`**

  `space = 8 + Counter::INIT_SPACE` виділяє байти для дискримінатора акаунта
  Anchor та полів `Counter` з `state.rs`. Дискримінатор допомагає Anchor
  підтвердити, що акаунт зберігає очікуваний тип перед його зчитуванням.

  **`seeds = [COUNTER_SEED]`**

  `seeds = [COUNTER_SEED]` вказує, що адреса акаунта лічильника має бути PDA,
  похідним від цього seed та ідентифікатора програми. З одним фіксованим seed
  існує один PDA лічильника для цієї програми. Щоб створити окремі лічильники в
  реальній програмі, зазвичай додають ще один seed, наприклад адресу користувача.

  **`bump`**

  `bump` вказує Anchor знайти та перевірити bump PDA — додатковий байт, який
  робить похідну адресу дійсною як PDA.

  **`Account<'info, Counter>`**

  `Account<'info, Counter>` вказує Anchor інтерпретувати дані акаунта як тип
  `Counter` з `state.rs`. Anchor також перевіряє, що акаунт належить цій
  програмі.

  **`Program<'info, System>`**

  `Program<'info, System>` вимагає від викликача надати System Program. Anchor
  використовує її для обмеження створення акаунта `init`. CPI переказу в
  обробнику також викликає System Program.

  **`handle_initialize`**

  Обробник виконується після того, як Anchor перевірить акаунти та створить акаунт
  лічильника, тому він може безпечно записати початкові дані акаунта.

  **`counter.count = 0`**

  Встановлює поле `count` в акаунті лічильника на `0`.

  **`counter.authority = ctx.accounts.payer.key()`**

  Встановлює поле `authority` в акаунті лічильника на адресу платника.

  **`system_program::Transfer`**

  Це акаунти, передані до інструкції переказу System Program. Цей CPI-переказ
  включено лише для демонстрації того, як CPI передає акаунти іншій програмі.

  **`CpiContext::new`**

  `CpiContext` пакує цільову програму та необхідні акаунти для Cross Program
  Invocation. Створення контексту підготовлює CPI, пов'язуючи програму, яку ви
  хочете викликати, з акаунтами, які ця програма очікує.

  **`system_program::transfer`**

  Цей CPI викликає інструкцію переказу System Program і переміщує
  `HELLO_WORLD_LAMPORTS` від платника до акаунта лічильника.

  **`msg!`**

  `msg!` записує повідомлення до журналів програми під час її виклику.
</Note>

### increment.rs

`increment.rs` визначає акаунти, необхідні для оновлення існуючого акаунта
лічильника. Обробник перевіряє, що підписант є збереженим власником, перевіряє,
що лічильник не досяг зазначеного `MAX_COUNT`, а потім збільшує лічильник.

```rust programs/my-program/src/instructions/increment.rs wrap
use anchor_lang::prelude::*;

use crate::{constants::*, error::ErrorCode, state::Counter};

#[derive(Accounts)]
pub struct Increment<'info> {
    #[account(
        mut,
        seeds = [COUNTER_SEED],
        bump
    )]
    pub counter: Account<'info, Counter>,
    pub authority: Signer<'info>,
}

pub fn handle_increment(ctx: Context<Increment>) -> Result<()> {
    require_keys_eq!(
        ctx.accounts.counter.authority,
        ctx.accounts.authority.key(),
        ErrorCode::Unauthorized,
    );
    require!(
        ctx.accounts.counter.count < MAX_COUNT,
        ErrorCode::CounterOverflow,
    );

    ctx.accounts.counter.count += 1;
    msg!("Hello, world! Counter is now {}", ctx.accounts.counter.count);
    Ok(())
}
```

<Note>
  **`derive(Accounts)`**

  `Increment` — це контекст акаунтів для інструкції `increment`. Anchor
  використовує його для перевірки змінного акаунту лічильника та необхідного
  підписанта.

  **`mut`**

  `mut` повідомляє Anchor, що обліковий запис лічильника має бути доступним
  для запису, оскільки обробник оновлює збережене значення `count`.

  **`seeds = [COUNTER_SEED]`**

  `seeds = [COUNTER_SEED]` перевіряє, що наданий обліковий запис лічильника є
  PDA, похідним від цього seed та ідентифікатора програми.

  **`bump`**

  `bump` повідомляє Anchor знайти та перевірити PDA bump для облікового запису
  лічильника.

  **`Account<'info, Counter>`**

  `Account<'info, Counter>` повідомляє Anchor десеріалізувати дані облікового
  запису як тип `Counter` з `state.rs`. Anchor також перевіряє, що обліковий
  запис належить цій програмі.

  **`Signer`**

  `Signer` вимагає підпису authority. Потім обробник порівнює адресу цього
  підписанта з authority, збереженим в обліковому записі лічильника.

  **`handle_increment`**

  Обробник запускається після того, як Anchor перевіряє список облікових записів,
  перевіряє право власності та десеріалізує обліковий запис лічильника.

  **`require_keys_eq!`**

  `require_keys_eq!` порівнює два публічні ключі та зупиняє інструкцію, якщо
  адреса підписанта не збігається з authority, збереженим в обліковому записі
  лічильника. Це правило авторизації на рівні застосунку цього шаблону.

  **`require!`**

  `require!` перевіряє булеве правило та зупиняє інструкцію з
  `CounterOverflow`, якщо лічильник вже досяг `MAX_COUNT`. Це правило
  шаблону демонструє користувацькі помилки та відмову до внесення змін.

  **`count += 1`**

  Тільки після того, як обидві перевірки пройдено, обробник оновлює дані
  облікового запису лічильника. Якщо будь-яка перевірка не пройдена, транзакція
  завершується невдачею і обліковий запис не змінюється.

  **`msg!`**

  `msg!` записує повідомлення до журналів програми під час її виклику.
</Note>

<Steps>
  <Step title="Account Context">
    Структура `Increment` визначає акаунти, які необхідно включити, коли
    користувач викликає інструкцію `increment`. Anchor перевіряє ці акаунти до
    запуску обробника.

  <Step title="Функція обробника">
    Функція `handle_increment` виконується після того, як Anchor перевіряє
    акаунти в `Increment`. Значення `ctx` надає обробнику доступ до цих
    перевірених акаунтів.

    ```rust increment.rs focus={12}

            mut,
            seeds = [COUNTER_SEED],
            bump
        )]
        pub counter: Account<'info, Counter>,
        pub authority: Signer<'info>,
    }

    pub fn handle_increment(ctx: Context<Increment>) -> Result<()> {
        require_keys_eq!(
            ctx.accounts.counter.authority,
            ctx.accounts.authority.key(),
            ErrorCode::Unauthorized,
        );
        require!(
            ctx.accounts.counter.count < MAX_COUNT,
            ErrorCode::CounterOverflow,
        );

        ctx.accounts.counter.count += 1;
        msg!("Hello, world! Counter is now {}", ctx.accounts.counter.count);
        Ok(())
    }
    ```
  </Step>

  <Step title="Перевірка повноважень">
    Перша перевірка переконується, що підписант має право оновлювати цей лічильник.
    Якщо адреса підписанта не збігається з `counter.authority`, інструкція
    зупиняється з помилкою `ErrorCode::Unauthorized`. Це демонструє авторизацію
    на рівні застосунку: програма володіє даними лічильника, але реалізує правило,
    яке визначає, який підписант може змінювати ці дані.

## Тестовий файл

`programs/my-program/tests/test_initialize.rs` є інтеграційним тестом на Rust.
Він не запускає локальний validator. Натомість завантажує скомпільований файл
`.so` у LiteSVM, будує транзакції, що викликають програму, та зчитує обліковий
запис лічильника після кожної транзакції. Тест будує інструкції для транзакції
Solana, вказуючи ідентифікатор програми, яку потрібно викликати, надаючи
instruction data та передаючи необхідні облікові записи.

```rust programs/my-program/tests/test_initialize.rs wrap
use {
    anchor_lang::{
        prelude::Pubkey,
        solana_program::{instruction::Instruction, system_program},
        AccountDeserialize, InstructionData, ToAccountMetas,
    },
    litesvm::LiteSVM,
    solana_keypair::Keypair,
    solana_message::{Message, VersionedMessage},
    solana_signer::Signer,
    solana_transaction::versioned::VersionedTransaction,
};

#[test]
fn test_initialize() {
    let program_id = my_program::id();
    let payer = Keypair::new();
    let counter = Pubkey::find_program_address(
        &[my_program::constants::COUNTER_SEED],
        &program_id,
    )
    .0;
    let mut svm = LiteSVM::new();
    let bytes = include_bytes!(concat!(
        env!("CARGO_TARGET_TMPDIR"),
        "/../deploy/my_program.so"
    ));
    svm.add_program(program_id, bytes).unwrap();
    svm.airdrop(&payer.pubkey(), 1_000_000_000).unwrap();

    let instruction = Instruction::new_with_bytes(
        program_id,
        &my_program::instruction::Initialize {}.data(),
        my_program::accounts::Initialize {
            payer: payer.pubkey(),
            counter,
            system_program: system_program::ID,
        }
        .to_account_metas(None),
    );

    let blockhash = svm.latest_blockhash();
    let msg = Message::new_with_blockhash(&[instruction], Some(&payer.pubkey()), &blockhash);
    let tx = VersionedTransaction::try_new(VersionedMessage::Legacy(msg), &[&payer]).unwrap();

    let res = svm.send_transaction(tx);
    assert!(res.is_ok());

    let counter_account = svm.get_account(&counter).unwrap();
    let mut data: &[u8] = &counter_account.data;
    let counter_state = my_program::state::Counter::try_deserialize(&mut data).unwrap();
    assert_eq!(counter_state.count, 0);
    assert_eq!(counter_state.authority, payer.pubkey());

    let instruction = Instruction::new_with_bytes(
        program_id,
        &my_program::instruction::Increment {}.data(),
        my_program::accounts::Increment {
            counter,
            authority: payer.pubkey(),
        }
        .to_account_metas(None),
    );

    let blockhash = svm.latest_blockhash();
    let msg = Message::new_with_blockhash(&[instruction], Some(&payer.pubkey()), &blockhash);
    let tx = VersionedTransaction::try_new(VersionedMessage::Legacy(msg), &[&payer]).unwrap();

    let res = svm.send_transaction(tx);
    assert!(res.is_ok());

    let counter_account = svm.get_account(&counter).unwrap();
    let mut data: &[u8] = &counter_account.data;
    let counter_state = my_program::state::Counter::try_deserialize(&mut data).unwrap();
    assert_eq!(counter_state.count, 1);
    assert_eq!(counter_state.authority, payer.pubkey());
}
```

<Note>
  **`litesvm::LiteSVM`**

  `LiteSVM` — це внутрішньопроцесна Solana VM для тестів. Вона дозволяє тесту
  реєструвати скомпільовану програму, створювати акаунти, надсилати транзакції та
  перевіряти стан акаунтів без запуску процесу validator.

  **`let program_id`**

  Тест отримує адресу програми зі значення `declare_id!` через
  `my_program::id()` та створює новий keypair платника для тестової
  транзакції.

  **`Pubkey::find_program_address`**

  Адреса лічильника виводиться з того самого `COUNTER_SEED`, що
  використовується програмою. Це дозволяє тесту звертатись до PDA, який очікує
  `initialize.rs`.

  **`include_bytes!`**

  `include_bytes!` зчитує скомпільований файл `my_program.so`, створений під
  час збірки. Ці байти є виконуваним кодом програми, який LiteSVM запустить у
  тесті.

  **`svm.add_program`**

  `svm.add_program` реєструє скомпільовані байти програми за адресою програми
  в LiteSVM. Аірдроп надає платнику достатньо локальних SOL для оплати транзакції
  та створення акаунту.

  **`let instruction`**

  `Instruction::new_with_bytes` створює інструкцію для виклику програми. Вона
  містить ідентифікатор програми, instruction data та акаунти інструкції.

  **`svm.latest_blockhash`**

  Кожна транзакція Solana потребує актуального blockhash. У цьому тесті LiteSVM
  надає blockhash для використання у транзакції.

  **`Message::new_with_blockhash`**

  Повідомлення містить інструкцію, платника комісії та blockhash. Це дані
  транзакції, які буде підписано.

  **`VersionedTransaction::try_new`**

  `VersionedTransaction::try_new` підписує повідомлення за допомогою keypair
  платника. Платник підписує, оскільки він сплачує комісію за транзакцію та
  фінансує новий акаунт лічильника.

  **`svm.send_transaction`**

  `svm.send_transaction` виконує транзакцію в LiteSVM.

  **`svm.get_account`**

  Після виконання транзакції тест зчитує акаунт лічильника безпосередньо з
  LiteSVM, щоб перевірити дані акаунту.

  **`Counter::try_deserialize`**

  Акаунт лічильника зберігає серіалізовані дані. `Counter::try_deserialize`
  перевіряє дискримінатор акаунту Anchor і перетворює дані акаунту назад у тип
  `Counter` з `state.rs`.

  **`assert_eq!(counter_state.count, 0)`**

  Після успішного виконання `initialize` тест десеріалізує акаунт лічильника
  та перевіряє, що початковий стан відповідає тому, що записав
  `handle_initialize`.

  **`assert_eq!(counter_state.count, 1)`**

  Після успішного виконання `increment` той самий акаунт лічильника повинен
  мати `count`, встановлений у `1`, зберігаючи при цьому того самого
  authority.
</Note>

## Конфігурація проєкту

Кореневі файли проєкту вказують Anchor та Cargo, як збирати, тестувати та
розгортати програму. Для повного довідника дивіться документацію Anchor для
[конфігурації Anchor.toml](https://www.anchor-lang.com/docs/references/anchor-toml)
та [Anchor CLI](https://www.anchor-lang.com/docs/references/cli).

```toml Anchor.toml
skip_local_validator = true

[toolchain]

[features]
resolution = true
skip-lint = false

[programs.localnet]
my_program = "82sFkffP9wxwpyfZyeaKHH2chQoJPUGsJZSPi9mrUuXd"

[provider]
cluster = "localnet"
wallet = "~/.config/solana/id.json"

[scripts]
test = "cargo test"

[hooks]
```

<Note>
  **`skip_local_validator`**

  `skip_local_validator = true` вказує Anchor не запускати validator для
  `anchor test`. Rust-тест натомість використовує LiteSVM.

  **`programs.localnet`**

  `[programs.localnet]` зіставляє назву крейту Rust із адресою програми, що
  використовується для локальних збірок і тестів.

  **`provider`**

  `[provider]` встановлює кластер і гаманець за замовчуванням для таких команд, як
  `anchor deploy`.

  **`scripts`**

  `[scripts]` змінює те, що виконує `anchor test`. У цьому шаблоні `anchor test`
  запускає `cargo test`.
</Note>
