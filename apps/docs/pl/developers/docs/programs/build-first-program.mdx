Ten szybki start wykorzystuje projekt startowy
[frameworka Anchor](https://www.anchor-lang.com/docs) wygenerowany przez
`anchor init`. Utworzysz projekt lokalnie, uruchomisz jego testy, zbudujesz
program i przejrzysz kod programu, który generuje Anchor.

## Wymagania wstępne

Zanim zaczniesz,
[zainstaluj narzędzia deweloperskie Solana](/developers/docs/quickstart).
Instalacja obejmuje Rust, Solana CLI oraz Anchor CLI.

Użyj Anchor CLI w wersji 1.1.2 lub wyższej dla tego szablonu. Sprawdź
zainstalowaną wersję:

```bash Terminal
anchor --version
```

<Steps titleSize="h3">

<Step title="Utwórz projekt">

Uruchom następujące polecenia w swoim terminalu:

```bash Terminal
anchor init my-program
cd my-program
```

Projekt startowy zawiera jeden program Solana w katalogu `programs/my-program`.
Program zawiera dwie instrukcje: jedną do inicjalizacji konta licznika i jedną
do inkrementacji licznika.

Niektóre części szablonu demonstrują typowe wzorce programów Solana:
wyprowadzanie adresów kont [PDA](/developers/docs/core/pda), wykonywanie Cross Program
Invocation ([CPI](/developers/docs/core/cpi)) w celu transferu SOL oraz używanie
niestandardowych sprawdzeń błędów do zatrzymania instrukcji, gdy warunek nie
jest spełniony.

</Step>

<Step title="Zbuduj Program">

Uruchom `anchor build`, aby skompilować program startowy:

```bash Terminal
anchor build
```

Skompilowany program jest zapisywany do `target/deploy/my_program.so`. Gdy
program zostanie wdrożony, zawartość tego pliku `.so` jest przechowywana na
koncie w łańcuchu.

</Step>

<Step title="Uruchom test">

Uruchom domyślny test:

```bash Terminal
anchor test
```

`Anchor.toml` tego szablonu używa polecenia testowego Rust:

```toml Anchor.toml
skip_local_validator = true

[scripts]
test = "cargo test"
```

Test ładuje skompilowany program do [LiteSVM](https://www.litesvm.com/), tworzy
płatnika, wysyła instrukcje `initialize` i `increment`, a następnie
sprawdza stan konta licznika.

Uruchomienie `anchor test` kompiluje również program, więc nie musisz uruchamiać
`anchor build` przed testowaniem lokalnym.

</Step>

<Step title="Wdróż program">

Testy lokalne zapewniają najszybszą pętlę informacji zwrotnej. Gdy będziesz
gotowy do wdrożenia w sieci, na przykład devnet, najpierw zbuduj projekt, a
następnie wdróż go do klastra.

Wdrożenie programu Solana wymaga SOL, ponieważ program jest przechowywany na
koncie, a konto musi opłacić zajmowaną przestrzeń. W sieci devnet możesz
bezpłatnie pozyskać devnet SOL z [Solana Faucet](https://faucet.solana.com/) lub
za pomocą Solana CLI:

```bash Terminal
solana airdrop 2 --url devnet
```

```bash Terminal
anchor build
anchor deploy --provider.cluster devnet
```

</Step>

</Steps>

## Pliki źródłowe

Katalog `src` zawiera program Solana. Dokumentacja Anchor dotycząca
[struktury programu](https://www.anchor-lang.com/docs/basics/program-structure)
omawiа podstawowe makra używane tutaj, w tym `declare_id!`,
`#[program]`, `#[derive(Accounts)]` i `#[account]`. Ta sekcja
przechodzi przez pliki szablonu.

### lib.rs

`lib.rs` jest punktem wejścia programu. Łączy pliki źródłowe, definiuje adres
programu oraz instrukcje programu, które użytkownicy mogą wywoływać.

```rust programs/my-program/src/lib.rs wrap
pub mod constants;
pub mod error;
pub mod instructions;
pub mod state;

use anchor_lang::prelude::*;

pub use constants::*;
pub use instructions::*;
pub use state::*;

declare_id!("82sFkffP9wxwpyfZyeaKHH2chQoJPUGsJZSPi9mrUuXd");

#[program]
pub mod my_program {
    use super::*;

    pub fn initialize(ctx: Context<Initialize>) -> Result<()> {
        crate::instructions::initialize::handle_initialize(ctx)
    }

    pub fn increment(ctx: Context<Increment>) -> Result<()> {
        crate::instructions::increment::handle_increment(ctx)
    }
}
```

<Note>
  **`pub mod constants`**

  `pub mod constants` włącza `constants.rs` do skrzynki programu. Tutaj
  szablon przechowuje współdzielone wartości programu, takie jak seed PDA, kwota
  przelewu i maksymalna wartość licznika.

  **`pub mod error`**

  `pub mod error` włącza `error.rs` do skrzynki programu. Ten plik definiuje
  niestandardowe błędy, które program może zwrócić, gdy instrukcja jest
  nieprawidłowa.

  **`pub mod instructions`**

  `pub mod instructions` włącza `instructions.rs` do skrzynki programu. Ten
  plik działa jak indeks dla plików specyficznych dla instrukcji w
  `src/instructions/`.

  **`pub mod state`**

  `pub mod state` włącza `state.rs` do skrzynki programu. Ten plik definiuje
  układ danych dla kont należących do tego programu, w tym konto `Counter`.

  **`anchor_lang::prelude`**

  `anchor_lang::prelude::*` importuje typy i makra Anchor używane do
  definiowania programu Solana, w tym `Context`, `Result`, `Pubkey`,
  `Account`, `Signer` oraz atrybuty kont Anchor.

  Linie `pub use` udostępniają publiczne elementy z modułów podrzędnych z
  poziomu korzenia skrzynki. Dzięki temu punkty wejścia instrukcji są krótkie, np.
  `Context<Initialize>` zamiast dłuższej ścieżki modułu.

  **`declare_id!`**

  `declare_id!` definiuje adres programu. Powinien być zgodny z adresem w
  `Anchor.toml`, wdrożonym program account oraz wszystkimi użytkownikami lub
  testami wywołującymi program.

  **`#[program]`**

  `#[program]` nakazuje Anchor wygenerowanie punktu wejścia programu Solana
  oraz kodu wysyłania instrukcji. Publiczne funkcje w tym module stają się
  instrukcjami, które użytkownicy mogą wywoływać.

  **`pub fn initialize`, `pub fn increment`**

  `initialize` i `increment` to dwie nazwy instrukcji, które użytkownicy
  mogą wywoływać. Każda otrzymuje `Context<T>`. Typ wewnątrz `Context`
  definiuje konta wymagane przez daną instrukcję, a Anchor weryfikuje te konta
  przed uruchomieniem instrukcji.

  **`handle_initialize`, `handle_increment`**

  Funkcja obsługi zawiera logikę instrukcji.
</Note>

### constants.rs

`constants.rs` przechowuje wspólne wartości w jednym miejscu. W tym szablonie
`COUNTER_SEED` wyprowadza PDA licznika, `HELLO_WORLD_LAMPORTS` jest
przekazywany podczas inicjalizacji, a `MAX_COUNT` jest sprawdzany przed
inkrementacją.

```rust programs/my-program/src/constants.rs wrap
use anchor_lang::prelude::*;

#[constant]
pub const COUNTER_SEED: &[u8] = b"counter";

#[constant]
pub const HELLO_WORLD_LAMPORTS: u64 = 1;

#[constant]
pub const MAX_COUNT: u64 = 10;
```

<Note>
  **`#[constant]`**

  `#[constant]` nakazuje Anchor uwzględnienie wartości w IDL programu. Dzięki
  temu ważne stałe programu są widoczne dla generowanych klientów i narzędzi.

  **`COUNTER_SEED`**

  `COUNTER_SEED` to ciąg bajtów używany do wyprowadzania PDA licznika. Zarówno
  program, jak i testy korzystają z tego seed, dzięki czemu są zgodne co do adresu
  konta bez konieczności przechowywania osobnego keypair. Ten szablon używa
  jednego stałego seed, więc program ma jeden adres licznika. Prawdziwe programy
  często zawierają adres użytkownika lub inny identyfikator w seeds, aby tworzyć
  wiele powiązanych kont.

  **`HELLO_WORLD_LAMPORTS`**

  `HELLO_WORLD_LAMPORTS` to ilość lamport przekazywanych od płatnika do konta
  licznika wewnątrz `initialize`. Jest celowo mała, ponieważ szablon
  demonstruje CPI do System Program.

  **`MAX_COUNT`**

  `MAX_COUNT` to górna granica sprawdzana przez `increment`.
  Przechowywanie jej tutaj zapewnia programowi, testom i wygenerowanemu IDL jedną
  wspólną nazwę dla tej reguły.
</Note>

    ```rust initialize.rs highlight={8,18} wrap
        // ...
        #[account(
    ```

  </div>

    - `COUNTER_SEED` wyznacza adres PDA licznika.
    - `HELLO_WORLD_LAMPORTS` określa kwotę
      przenoszoną od płatnika na konto licznika.
  </div>
</Columns>

### state.rs

`state.rs` definiuje niestandardowe typy danych dla kont tworzonych i
posiadanych przez program. Program definiuje instrukcje tworzenia, inicjowania i
aktualizowania tych danych, jednak dane licznika nie są przechowywane w samym
programie. Są przechowywane w oddzielnym koncie z własnym adresem.

```rust programs/my-program/src/state.rs wrap
use anchor_lang::prelude::*;

#[account]
#[derive(InitSpace)]
pub struct Counter {
    pub count: u64,
    pub authority: Pubkey,
}
```

<Note>
  **`#[account]`**

  `#[account]` informuje Anchor, że ta struktura to dane, które mogą być
  przechowywane w koncie onchain należącym do tego programu. Anchor używa jej do
  serializacji, deserializacji i walidacji kont `Counter`.

  **`InitSpace`**

  `InitSpace` pozwala Anchor obliczyć `Counter::INIT_SPACE`, czyli liczbę
  bajtów potrzebnych dla pól tej struktury. 8-bajtowy dyskryminator konta Anchor
  jest dodawany osobno podczas tworzenia konta.

  **`count`**

  `count` to wartość licznika przechowywana w danych konta.

  **`authority`**

  `authority` przechowuje adres uprawniony do inkrementacji licznika.
  `initialize` zapisuje ten adres, a `increment` wymaga podpisania tym
  samym adresem.
</Note>

<Columns cols={2}>
  <div>

    ```rust initialize.rs highlight={4,12-13} wrap
    }
    ```


  </div>

  <div>
    `state.rs` definiuje dane konta `Counter`. Pliki instrukcji używają tego
    typu podczas tworzenia i aktualizowania konta:

    - `Counter::INIT_SPACE` określa rozmiar konta dla
      pól zdefiniowanych w `state.rs`.
    - `count` i `authority` to wartości pól
      zapisywane podczas inicjalizacji konta.
    - `count += 1` aktualizuje przechowywaną wartość
      licznika po pomyślnej weryfikacji.
  </div>
</Columns>

### error.rs

`error.rs` definiuje niestandardowe błędy programu. W tym szablonie błędy
przedstawiają, jak handlery instrukcji zatrzymują się, gdy wywołujący nie ma
uprawnień do aktualizacji licznika lub licznik osiągnął już `MAX_COUNT`.

```rust programs/my-program/src/error.rs wrap
use anchor_lang::prelude::*;

#[error_code]
pub enum ErrorCode {
    #[msg("Only the counter authority can update this counter")]
    Unauthorized,
    #[msg("Counter has reached the maximum value")]
    CounterOverflow,
}
```

<Note>
  **`#[error_code]`**

  `#[error_code]` informuje Anchor, aby zamienił te warianty w niestandardowe
  błędy programu. Klienty i testy mogą używać tych błędów zamiast zgadywać na
  podstawie surowych kodów błędów.

  **`Unauthorized`**

  `Unauthorized` jest zwracany, gdy podpisujący transakcję nie jest authority
  przechowywanym na koncie licznika.

  **`CounterOverflow`**

  `CounterOverflow` jest zwracany, gdy inkrementacja naruszyłaby regułę
  `MAX_COUNT` programu.
</Note>

<Columns cols={2}>
  <div>
    ```rust increment.rs highlight={5,9} wrap
    pub fn handle_increment(ctx: Context<Increment>) -> Result<()> {
        require_keys_eq!(
            ctx.accounts.counter.authority,
            ctx.accounts.authority.key(),
            ErrorCode::Unauthorized,
        );
        require!(
            ctx.accounts.counter.count < MAX_COUNT,
            ErrorCode::CounterOverflow,
        );

        ctx.accounts.counter.count += 1;
        msg!("Hello, world! Counter is now {}", ctx.accounts.counter.count);
        Ok(())
    }
    ```
  </div>

  <div>
    `error.rs` określa błędy, które instrukcja może zwrócić:

    - `ErrorCode::Unauthorized` jest zwracany, gdy
      podpisujący nie jest authority przechowywanym na koncie licznika.
    - `ErrorCode::CounterOverflow` jest zwracany, gdy
      licznik osiągnął już `MAX_COUNT`.
  </div>
</Columns>

### instructions.rs

`instructions.rs` łączy pliki instrukcji z kratem programu, dzięki czemu
`lib.rs` może uzyskać dostęp do kodu instrukcji `initialize` i
`increment`. Każdy plik instrukcji definiuje konta wymagane przez daną
instrukcję oraz logikę obsługi wykonywaną po tym, jak Anchor zweryfikuje te
konta.

```rust programs/my-program/src/instructions.rs wrap
pub mod initialize;
pub mod increment;

pub use initialize::*;
pub use increment::*;
```

<Note>
  **`pub mod initialize`**

  Linie `pub mod` sprawiają, że `src/instructions/initialize.rs` i
  `src/instructions/increment.rs` stają się częścią krata programu.

  **`pub use initialize`**

  Linie `pub use` ponownie eksportują publiczne elementy z tych plików. Dzięki
  temu struktury kont instrukcji i funkcje obsługi są dostępne poprzez moduł
  `instructions`.
</Note>

### initialize.rs

`initialize.rs` definiuje konta wymagane do utworzenia konta licznika, a
następnie zapisuje jego pierwsze wartości. Struktura `#[derive(Accounts)]`
korzysta z
[ograniczeń kont](https://www.anchor-lang.com/docs/references/account-constraints)
Anchor, aby określić, które konta są wymagane i w jaki sposób tworzone jest nowe
konto licznika.

```rust programs/my-program/src/instructions/initialize.rs wrap
use anchor_lang::prelude::*;

use crate::{constants::*, state::Counter};

#[derive(Accounts)]
pub struct Initialize<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,
    #[account(
        init,
        payer = payer,
        space = 8 + Counter::INIT_SPACE,
        seeds = [COUNTER_SEED],
        bump
    )]
    pub counter: Account<'info, Counter>,
    pub system_program: Program<'info, System>,
}

pub fn handle_initialize(ctx: Context<Initialize>) -> Result<()> {
    ctx.accounts.counter.count = 0;
    ctx.accounts.counter.authority = ctx.accounts.payer.key();

    let cpi_accounts = anchor_lang::system_program::Transfer {
        from: ctx.accounts.payer.to_account_info(),
        to: ctx.accounts.counter.to_account_info(),
    };
    let cpi_ctx = CpiContext::new(anchor_lang::system_program::ID, cpi_accounts);
    anchor_lang::system_program::transfer(cpi_ctx, HELLO_WORLD_LAMPORTS)?;

    msg!("Hello, world! Counter initialized");
    Ok(())
}
```

<Note>
  Ten plik importuje współdzielone stałe oraz typ konta `Counter`. Instrukcja
  używa tych definicji do wyprowadzenia PDA, wyboru kwoty transferu oraz
  przydzielenia konta z odpowiednim rozmiarem danych.

  **`derive(Accounts)`**

  `Initialize` jest kontekstem kont dla instrukcji `initialize`. Każde
  pole w strukturze reprezentuje oddzielne konto, które musi zostać dołączone
  podczas wywoływania instrukcji. Anchor używa tej struktury do walidacji
  przychodzących kont przed uruchomieniem handlera.

  **`#[account(mut)]`**

  `#[account(mut)]` informuje Anchor, że konto płatnika musi być zapisywalne.
  Jest to wymagane, ponieważ zarówno tworzenie konta, jak i transfer CPI odejmują
  lamports od płatnika.

  **`Signer<'info>`**

  `Signer<'info>` informuje Anchor, że płatnik musi podpisać transakcję.

  **`#[account(`**

  Blok `#[account(...)]` informuje Anchor, jak utworzyć i zwalidować konto
  licznika przed uruchomieniem handlera.

  **`init`**

  `init` mówi Anchor, aby utworzył konto `counter` przed uruchomieniem
  handlera. Nowe konto należy do tego programu, więc program może przechowywać w
  nim dane `Counter`.

  **`payer = payer`**

  `payer = payer` wskazuje konto `payer` jako płatnika za utworzenie
  nowego konta licznika.

  **`space = 8 + Counter::INIT_SPACE`**

  `space = 8 + Counter::INIT_SPACE` przydziela bajty na dyskryminator konta
  Anchor oraz pola `Counter` z `state.rs`. Dyskryminator pomaga Anchor
  potwierdzić, że konto przechowuje oczekiwany typ przed jego odczytaniem.

  **`seeds = [COUNTER_SEED]`**

  `seeds = [COUNTER_SEED]` oznacza, że adres konta licznika musi być PDA
  wyprowadzonym z tego seed i identyfikatora programu. Przy jednym stałym seed
  istnieje jeden licznik PDA dla tego programu. Aby tworzyć osobne liczniki w
  prawdziwym programie, zazwyczaj należałoby dodać kolejny seed, na przykład adres
  użytkownika.

  **`bump`**

  `bump` nakazuje Anchor znalezienie i zweryfikowanie bumpa PDA, czyli
  dodatkowego bajtu, który sprawia, że wyprowadzony adres jest prawidłowy jako
  PDA.

  **`Account<'info, Counter>`**

  `Account<'info, Counter>` nakazuje Anchor traktowanie danych konta jako typu
  `Counter` z `state.rs`. Anchor sprawdza również, czy konto należy do tego
  programu.

  **`Program<'info, System>`**

  `Program<'info, System>` wymaga od wywołującego podania System Program.
  Anchor używa go do ograniczenia tworzenia konta `init`. Transfer CPI w
  handlerze również wywołuje System Program.

  **`handle_initialize`**

  Handler uruchamia się po tym, jak Anchor zweryfikuje konta i utworzy konto
  licznika, dzięki czemu może bezpiecznie zapisać początkowe dane konta.

  **`counter.count = 0`**

  Ustawia pole `count` w koncie licznika na `0`.

  **`counter.authority = ctx.accounts.payer.key()`**

  Ustawia pole `authority` w koncie licznika na adres płatnika.

  **`system_program::Transfer`**

  Są to konta przekazywane do instrukcji transferu System Program. Ten transfer

### increment.rs

`increment.rs` definiuje konta wymagane do aktualizacji istniejącego konta
licznika. Handler sprawdza, czy podpisujący jest zapisanym administratorem,
sprawdza, czy licznik nie osiągnął określonego `MAX_COUNT`, a następnie
inkrementuje licznik.

```rust programs/my-program/src/instructions/increment.rs wrap
use anchor_lang::prelude::*;

use crate::{constants::*, error::ErrorCode, state::Counter};

#[derive(Accounts)]
pub struct Increment<'info> {
    #[account(
        mut,
        seeds = [COUNTER_SEED],
        bump
    )]
    pub counter: Account<'info, Counter>,
    pub authority: Signer<'info>,
}

pub fn handle_increment(ctx: Context<Increment>) -> Result<()> {
    require_keys_eq!(
        ctx.accounts.counter.authority,
        ctx.accounts.authority.key(),
        ErrorCode::Unauthorized,
    );
    require!(
        ctx.accounts.counter.count < MAX_COUNT,
        ErrorCode::CounterOverflow,
    );

    ctx.accounts.counter.count += 1;
    msg!("Hello, world! Counter is now {}", ctx.accounts.counter.count);
    Ok(())
}
```

<Note>
  **`derive(Accounts)`**

  `Increment` to kontekst konta dla instrukcji `increment`. Anchor używa
  go do weryfikacji mutowalnego konta licznika i wymaganego sygnatariusza.

  **`mut`**

  `mut` informuje Anchor, że konto licznika musi być zapisywalne, ponieważ
  handler aktualizuje przechowywaną wartość `count`.

  **`seeds = [COUNTER_SEED]`**

  `seeds = [COUNTER_SEED]` weryfikuje, że podane konto licznika jest PDA
  wyprowadzonym z tego seed i identyfikatora programu.

  **`bump`**

  `bump` informuje Anchor, aby znalazł i zweryfikował bump PDA dla konta
  licznika.

  **`Account<'info, Counter>`**

  `Account<'info, Counter>` informuje Anchor, aby zdeserializował dane konta
  jako typ `Counter` z `state.rs`. Anchor sprawdza również, czy konto jest
  własnością tego programu.

  **`Signer`**

  `Signer` wymaga podpisu authority. Handler następnie porównuje adres tego
  podpisującego z authority przechowywanym na koncie licznika.

  **`handle_increment`**

  Handler uruchamia się po tym, jak Anchor zwaliduje listę kont, sprawdzi własność
  i zdeserializuje konto licznika.

  **`require_keys_eq!`**

  `require_keys_eq!` porównuje dwa klucze publiczne i zatrzymuje instrukcję,
  jeśli adres podpisującego nie pasuje do authority przechowywanego na koncie
  licznika. Jest to reguła autoryzacji na poziomie aplikacji tego szablonu.

  **`require!`**

  `require!` sprawdza regułę logiczną i zatrzymuje instrukcję z
  `CounterOverflow`, jeśli licznik osiągnął już `MAX_COUNT`. Ta reguła
  szablonu demonstruje niestandardowe błędy i przerywanie przed mutacją.

  **`count += 1`**

  Dopiero po pomyślnym przejściu obu sprawdzeń handler aktualizuje dane konta
  licznika. Jeśli którekolwiek ze sprawdzeń nie powiedzie się, transakcja kończy
  się niepowodzeniem i konto nie zostaje zmienione.

  **`msg!`**

  `msg!` zapisuje wiadomość w logach programu, gdy program jest wywoływany.
</Note>

    ```rust increment.rs focus={24-25}
            mut,
            seeds = [COUNTER_SEED],
            bump
        )]
        pub counter: Account<'info, Counter>,
        pub authority: Signer<'info>,
    }

    pub fn handle_increment(ctx: Context<Increment>) -> Result<()> {
        require_keys_eq!(
            ctx.accounts.counter.authority,
            ctx.accounts.authority.key(),
            ErrorCode::Unauthorized,
        );
        require!(
            ctx.accounts.counter.count < MAX_COUNT,
            ErrorCode::CounterOverflow,
        );

        ctx.accounts.counter.count += 1;
        msg!("Hello, world! Counter is now {}", ctx.accounts.counter.count);
        Ok(())
    }
    ```
  </Step>
</Steps>

```rust programs/my-program/tests/test_initialize.rs wrap
use {
    anchor_lang::{
        prelude::Pubkey,
        solana_program::{instruction::Instruction, system_program},
        AccountDeserialize, InstructionData, ToAccountMetas,
    },
    litesvm::LiteSVM,
    solana_keypair::Keypair,
    solana_message::{Message, VersionedMessage},
    solana_signer::Signer,
    solana_transaction::versioned::VersionedTransaction,
};

#[test]
fn test_initialize() {
    let program_id = my_program::id();
    let payer = Keypair::new();
    let counter = Pubkey::find_program_address(
        &[my_program::constants::COUNTER_SEED],
        &program_id,
    )
    .0;
    let mut svm = LiteSVM::new();
    let bytes = include_bytes!(concat!(
        env!("CARGO_TARGET_TMPDIR"),
        "/../deploy/my_program.so"
    ));
    svm.add_program(program_id, bytes).unwrap();
    svm.airdrop(&payer.pubkey(), 1_000_000_000).unwrap();

    let instruction = Instruction::new_with_bytes(
        program_id,
        &my_program::instruction::Initialize {}.data(),
        my_program::accounts::Initialize {
            payer: payer.pubkey(),
            counter,
            system_program: system_program::ID,
        }
        .to_account_metas(None),
    );

    let blockhash = svm.latest_blockhash();
    let msg = Message::new_with_blockhash(&[instruction], Some(&payer.pubkey()), &blockhash);
    let tx = VersionedTransaction::try_new(VersionedMessage::Legacy(msg), &[&payer]).unwrap();

    let res = svm.send_transaction(tx);
    assert!(res.is_ok());

    let counter_account = svm.get_account(&counter).unwrap();
    let mut data: &[u8] = &counter_account.data;
    let counter_state = my_program::state::Counter::try_deserialize(&mut data).unwrap();
    assert_eq!(counter_state.count, 0);
    assert_eq!(counter_state.authority, payer.pubkey());

    let instruction = Instruction::new_with_bytes(
        program_id,
        &my_program::instruction::Increment {}.data(),
        my_program::accounts::Increment {
            counter,
            authority: payer.pubkey(),
        }
        .to_account_metas(None),
    );

    let blockhash = svm.latest_blockhash();
    let msg = Message::new_with_blockhash(&[instruction], Some(&payer.pubkey()), &blockhash);
    let tx = VersionedTransaction::try_new(VersionedMessage::Legacy(msg), &[&payer]).unwrap();

    let res = svm.send_transaction(tx);
    assert!(res.is_ok());

    let counter_account = svm.get_account(&counter).unwrap();
    let mut data: &[u8] = &counter_account.data;
    let counter_state = my_program::state::Counter::try_deserialize(&mut data).unwrap();
    assert_eq!(counter_state.count, 1);
    assert_eq!(counter_state.authority, payer.pubkey());
}
```

<Note>
  **`litesvm::LiteSVM`**

  `LiteSVM` to wbudowana maszyna wirtualna Solana przeznaczona do testów.
  Umożliwia testowi rejestrację skompilowanego programu, tworzenie kont, wysyłanie
  transakcji oraz inspekcję stanu kont bez uruchamiania procesu validator.

  **`let program_id`**

  Test pobiera adres programu z wartości `declare_id!` za pomocą
  `my_program::id()` i tworzy nowy keypair płatnika dla transakcji testowej.

  **`Pubkey::find_program_address`**

  Adres licznika jest wyprowadzany z tego samego `COUNTER_SEED`, którego używa
  program. Dzięki temu test celuje w PDA, którego oczekuje `initialize.rs`.

  **`include_bytes!`**

  `include_bytes!` odczytuje skompilowany plik `my_program.so` wygenerowany
  przez build. Te bajty stanowią wykonywalny kod programu, który LiteSVM uruchomi
  w trakcie testu.

  **`svm.add_program`**

  `svm.add_program` rejestruje skompilowane bajty programu pod adresem
  programu w LiteSVM. Airdrop zapewnia płatnikowi wystarczającą ilość lokalnych
  SOL, aby opłacić transakcję i utworzenie konta.

  **`let instruction`**

  `Instruction::new_with_bytes` tworzy instrukcję wywołania programu. Zawiera
  ona identyfikator programu, instruction data oraz konta instrukcji.

  **`svm.latest_blockhash`**

  Każda transakcja Solana wymaga aktualnego blockhasha. W tym teście LiteSVM
  dostarcza blockhash do użycia w transakcji.

  **`Message::new_with_blockhash`**

  Wiadomość zawiera instrukcję, płatnika opłat oraz blockhash. Są to dane
  transakcji, które zostaną podpisane.

  **`VersionedTransaction::try_new`**

  `VersionedTransaction::try_new` podpisuje wiadomość za pomocą keypair
  płatnika. Płatnik podpisuje, ponieważ uiszcza opłatę transakcyjną i finansuje
  nowe konto licznika.

  **`svm.send_transaction`**

  `svm.send_transaction` wykonuje transakcję w LiteSVM.

  **`svm.get_account`**

  Po wykonaniu transakcji test odczytuje konto licznika bezpośrednio z LiteSVM,
  aby móc sprawdzić dane konta.

  **`Counter::try_deserialize`**

  Konto licznika przechowuje zserializowane dane. `Counter::try_deserialize`
  sprawdza dyskryminator konta Anchor i przekształca dane konta z powrotem w typ
  `Counter` z `state.rs`.

  **`assert_eq!(counter_state.count, 0)`**

  Po pomyślnym wykonaniu `initialize` test deserializuje konto licznika i
  sprawdza, czy stan początkowy odpowiada temu, co zapisał
  `handle_initialize`.

  **`assert_eq!(counter_state.count, 1)`**

  Po pomyślnym wykonaniu `increment` to samo konto licznika powinno mieć
  `count` ustawione na `1`, zachowując przy tym tego samego właściciela.
</Note>

<Note>
  **`skip_local_validator`**

  `skip_local_validator = true` informuje Anchor, aby nie uruchamiał validator dla
  `anchor test`. Test Rust używa zamiast tego LiteSVM.

  **`programs.localnet`**

  `[programs.localnet]` mapuje nazwę skrzynki Rust na adres programu używany
  podczas loklanego budowania i testowania.

  **`provider`**

  `[provider]` ustawia domyślny klaster i portfel dla poleceń takich jak
  `anchor deploy`.

  **`scripts`**

  `[scripts]` zmienia to, co uruchamia `anchor test`. W tym szablonie
  `anchor test` uruchamia `cargo test`.
</Note>
