h1: Créez votre premier programme Solana
---

Ce démarrage rapide utilise le projet de démarrage du
[framework Anchor](https://www.anchor-lang.com/docs) généré par `anchor init`.
Vous allez créer le projet localement, exécuter ses tests, compiler le programme
et parcourir le code du programme qu'Anchor génère.

## Prérequis

Avant de commencer,
[installez les outils de développement Solana](/docs/intro/installation).
L'installation inclut Rust, la CLI Solana et la CLI Anchor.

Utilisez la version 1.1.2 ou supérieure de la CLI Anchor pour ce modèle.
Vérifiez votre version installée :

```bash Terminal
anchor --version
```

<Steps>

<Step>

### Créer le projet

Exécutez les commandes suivantes dans votre terminal :

```bash Terminal
anchor init my-program
cd my-program
```

Le projet de démarrage comprend un programme Solana sous `programs/my-program`.
Le programme comprend deux instructions : une pour initialiser un compte
compteur et une pour incrémenter le compteur.

Certaines parties du modèle illustrent des patterns courants des programmes
Solana : la dérivation d'adresses de compte [PDA](/docs/core/pda), l'exécution
d'un Cross Program Invocation ([CPI](/docs/core/cpi)) pour transférer des SOL,
et l'utilisation de vérifications d'erreurs personnalisées pour arrêter une
instruction lorsqu'une condition échoue.

<Step>

### Compiler le programme

Exécutez `anchor build` pour compiler le programme de démarrage :

```bash Terminal
anchor build
```

Le programme compilé est écrit dans `target/deploy/my_program.so`. Lorsque le
programme est déployé, le contenu de ce fichier `.so` est stocké dans un compte
on-chain.

</Step>

<Step>

### Exécuter le test

Exécutez le test par défaut :

```bash Terminal
anchor test
```

Le `Anchor.toml` de ce modèle utilise la commande de test Rust :

```toml title="Anchor.toml"
skip_local_validator = true

[scripts]
test = "cargo test"
```

Le test charge le programme compilé dans [LiteSVM](https://www.litesvm.com/),
créé un payeur, envoie les instructions _rs`initialize`_ et _rs`increment`_,
puis vérifie l'état du compte compteur.

L'exécution de `anchor test` compile également le programme, vous n'avez donc
pas besoin d'exécuter `anchor build` en premier lors des tests en local.

</Step>

<Step>

### Déployer le programme

Les tests locaux offrent la boucle de rétroaction la plus rapide. Lorsque vous
êtes prêt à déployer sur un réseau, par exemple devnet, compilez d'abord, puis
déployez sur un cluster.

Le déploiement d'un programme Solana nécessite des SOL car le programme est
stocké dans un program account, et celui-ci doit payer pour l'espace qu'il
utilise. Sur devnet, demandez des SOL devnet gratuits depuis le
[Solana Faucet](https://faucet.solana.com/) ou via le Solana CLI :

```bash Terminal
solana airdrop 2 --url devnet
```

```bash Terminal
anchor build
anchor deploy --provider.cluster devnet
```

</Step>

</Steps>

## Fichiers sources

Le répertoire `src` contient le programme Solana. La documentation d'Anchor sur
la
[Structure du programme](https://www.anchor-lang.com/docs/basics/program-structure)
explique les macros principales utilisées ici, notamment _rs`declare_id!`_,
_rs`#[program]`_, _rs`#[derive(Accounts)]`_ et _rs`#[account]`_. Cette section
parcourt les fichiers du modèle.

### lib.rs

`lib.rs` est le point d'entrée du programme. Il relie les fichiers sources,
définit l'adresse du programme et définit les instructions du programme que les
utilisateurs peuvent appeler.

```rust title="programs/my-program/src/lib.rs" -w
pub mod constants;
pub mod error;
pub mod instructions;
pub mod state;

use anchor_lang::prelude::*;

pub use constants::*;
pub use instructions::*;
pub use state::*;

declare_id!("82sFkffP9wxwpyfZyeaKHH2chQoJPUGsJZSPi9mrUuXd");

#[program]
pub mod my_program {
    use super::*;

    pub fn initialize(ctx: Context<Initialize>) -> Result<()> {
        crate::instructions::initialize::handle_initialize(ctx)
    }

    pub fn increment(ctx: Context<Increment>) -> Result<()> {
        crate::instructions::increment::handle_increment(ctx)
    }
}
```

<Note>
  **`pub mod constants`**

  _rs`pub mod constants`_ intègre `constants.rs` dans la crate du programme. C'est
  ici que le modèle conserve les valeurs partagées du programme, telles que le
  seed PDA, le montant du transfert et la valeur maximale du compteur.

  **`pub mod error`**

  _rs`pub mod error`_ intègre `error.rs` dans la crate du programme. Ce fichier
  définit les erreurs personnalisées que le programme peut retourner lorsqu'une
  instruction est invalide.

  **`pub mod instructions`**

  _rs`pub mod instructions`_ intègre `instructions.rs` dans la crate du programme.
  Ce fichier fonctionne comme un index pour les fichiers spécifiques aux
  instructions dans `src/instructions/`.

  **`pub mod state`**

  _rs`pub mod state`_ intègre `state.rs` dans la crate du programme. Ce fichier
  définit la structure des données pour les comptes appartenant à ce programme, y
  compris le compte _rs`Counter`_.

  **`anchor_lang::prelude`**

  _rs`anchor_lang::prelude::*`_ importe les types et macros Anchor utilisés pour
  définir un programme Solana, notamment _rs`Context`_, _rs`Result`_,
  _rs`Pubkey`_, _rs`Account`_, _rs`Signer`_, et les attributs de compte Anchor.

  Les lignes _rs`pub use`_ rendent publics les éléments des modules enfants depuis
  la racine de la crate. Cela permet de raccourcir les points d'entrée des
  instructions, par exemple _rs`Context<Initialize>`_ au lieu d'un chemin de
  module plus long.

  **`declare_id!`**

  _rs`declare_id!`_ définit l'adresse du programme. Elle doit correspondre à
  l'adresse dans `Anchor.toml`, le program account déployé, et tout utilisateur ou
  test qui appelle le programme.

  **`#[program]`**

  _rs`#[program]`_ indique à Anchor de générer le point d'entrée du programme
  Solana et le code de dispatch des instructions. Les fonctions publiques de ce
  module deviennent les instructions que les utilisateurs peuvent appeler.

  **`pub fn initialize`, `pub fn increment`**

  _rs`initialize`_ et _rs`increment`_ sont les deux noms d'instructions que les
  utilisateurs peuvent appeler. Chacune reçoit un _rs`Context<T>`_. Le type à
  l'intérieur de _rs`Context`_ définit les comptes requis par cette instruction,
  et Anchor valide ces comptes avant l'exécution de l'instruction.

  **`handle_initialize`, `handle_increment`**

  La fonction de traitement contient la logique de l'instruction.
</Note>

### constants.rs

`constants.rs` regroupe les valeurs partagées en un seul endroit. Dans ce
modèle, _rs`COUNTER_SEED`_ dérive le PDA du compteur, _rs`HELLO_WORLD_LAMPORTS`_
est transféré lors de l'initialisation, et _rs`MAX_COUNT`_ est vérifié avant
l'incrémentation.

```rust title="programs/my-program/src/constants.rs" -w
use anchor_lang::prelude::*;

#[constant]
pub const COUNTER_SEED: &[u8] = b"counter";

#[constant]
pub const HELLO_WORLD_LAMPORTS: u64 = 1;

#[constant]
pub const MAX_COUNT: u64 = 10;
```

<Note>
  **`#[constant]`**

  _rs`#[constant]`_ indique à Anchor d'inclure la valeur dans l'IDL du programme.
  Cela rend les constantes importantes du programme visibles pour les clients
  générés et les outils.

  **`COUNTER_SEED`**

  _rs`COUNTER_SEED`_ est la chaîne d'octets utilisée pour dériver le PDA du
  compteur. Le programme et les tests utilisent tous les deux ce seed afin de
  s'accorder sur l'adresse du compte sans stocker un keypair séparé. Ce modèle
  utilise un seed fixe unique, de sorte que le programme ne possède qu'une seule
  adresse de compteur. Les programmes réels incluent souvent l'adresse d'un
  utilisateur ou un autre identifiant dans les seeds pour créer de nombreux
  comptes associés.

  **`HELLO_WORLD_LAMPORTS`**

  _rs`HELLO_WORLD_LAMPORTS`_ est le montant de lamports transféré du payeur vers
  le program account dans _rs`initialize`_. Il est volontairement infime car le
  modèle illustre un CPI vers le System Program.

  **`MAX_COUNT`**

  _rs`MAX_COUNT`_ est la limite supérieure vérifiée par _rs`increment`_. La
  conserver ici permet au programme, aux tests et à l'IDL généré de partager un
  nom unique pour cette règle.
</Note>

### state.rs

`state.rs` définit des types de données personnalisés pour les comptes que le
programme crée et possède. Le programme définit des instructions pour créer,
initialiser et mettre à jour ces données, mais les données du compteur ne sont
pas stockées dans le programme lui-même. Elles sont stockées dans un compte
séparé possédant sa propre adresse.

```rust title="programs/my-program/src/state.rs" -w
use anchor_lang::prelude::*;

#[account]
#[derive(InitSpace)]
pub struct Counter {
    pub count: u64,
    pub authority: Pubkey,
}
```

<Note>
  **`#[account]`**

  _rs`#[account]`_ indique à Anchor que cette structure est une donnée pouvant
  être stockée dans un compte onchain appartenant à ce programme. Anchor l'utilise
  pour sérialiser, désérialiser et valider les comptes _rs`Counter`_.

  **`InitSpace`**

  _rs`InitSpace`_ permet à Anchor de calculer _rs`Counter::INIT_SPACE`_, le nombre
  d'octets nécessaires pour les champs de cette structure. Le discriminateur de
  compte Anchor de 8 octets est ajouté séparément lors de la création du compte.

  **`count`**

  _rs`count`_ est la valeur du compteur stockée dans les données du compte.

  **`authority`**

  _rs`authority`_ stocke l'adresse autorisée à incrémenter le compteur.
  _rs`initialize`_ écrit cette adresse, et _rs`increment`_ exige que cette même
  adresse signe.
</Note>

<Columns cols={2}>
  <div>
    ```rust title="initialize.rs" -w

        // !mark
        space = 8 + Counter::INIT_SPACE,

        ctx.accounts.counter.count = 0;
        ctx.accounts.counter.authority = ctx.accounts.payer.key();

        Ok(())
    }
    ```

    ```rust title="increment.rs" -w

        // ...

        // !mark
        ctx.accounts.counter.count += 1;
        Ok(())
    }
    ```
  </div>

  <div>
    `state.rs` définit les données du compte _rs`Counter`_. Les fichiers
    d'instruction utilisent ce type lors de la création et de la mise à jour du
    compte :

    - _rs`Counter::INIT_SPACE`_ dimensionne le compte pour
      les champs définis dans `state.rs`.
    - _rs`count`_ et _rs`authority`_ sont les valeurs
      de champs écrites lors de l'initialisation du compte.
    - _rs`count += 1`_ met à jour la valeur du compteur
      stockée une fois la validation réussie.
  </div>
</Columns>

### error.rs

`error.rs` définit les erreurs personnalisées du programme. Dans ce modèle, les
erreurs montrent comment les gestionnaires d'instructions s'arrêtent lorsqu'un
appelant n'est pas autorisé à mettre à jour le compteur ou que celui-ci a déjà
atteint _rs`MAX_COUNT`_.

```rust title="programs/my-program/src/error.rs" -w
use anchor_lang::prelude::*;

#[error_code]
pub enum ErrorCode {
    #[msg("Only the counter authority can update this counter")]
    Unauthorized,
    #[msg("Counter has reached the maximum value")]
    CounterOverflow,
}
```

<Note>
  **`#[error_code]`**

  _rs`#[error_code]`_ indique à Anchor de transformer ces variantes en erreurs de
  programme personnalisées. Les clients et les tests peuvent utiliser ces erreurs
  plutôt que de deviner à partir de codes d'erreur bruts.

  **`Unauthorized`**

  _rs`Unauthorized`_ est retourné lorsque le signataire de la transaction n'est
  pas l'autorité stockée dans le compte du compteur.

  **`CounterOverflow`**

  _rs`CounterOverflow`_ est retourné lorsqu'un incrément enfreindrait la règle
  _rs`MAX_COUNT`_ du programme.
</Note>

<Columns cols={2}>
  <div>
    ```rust title="increment.rs" -w
    pub fn handle_increment(ctx: Context<Increment>) -> Result<()> {
        require_keys_eq!(
            ctx.accounts.counter.authority,
            ctx.accounts.authority.key(),

        );

        ctx.accounts.counter.count += 1;
        msg!("Hello, world! Counter is now {}", ctx.accounts.counter.count);
        Ok(())
    }
    ```
  </div>

  <div>
    `error.rs` nomme les erreurs que l'instruction peut retourner :

    - _rs`ErrorCode::Unauthorized`_ est retourné
      lorsque le signataire n'est pas l'autorité stockée dans le compte du compteur.
    - _rs`ErrorCode::CounterOverflow`_ est retourné
      lorsque le compteur a déjà atteint _rs`MAX_COUNT`_.
  </div>
</Columns>

### instructions.rs

`instructions.rs` connecte les fichiers d'instructions au crate du programme
afin que `lib.rs` puisse accéder au code des instructions _rs`initialize`_ et
_rs`increment`_. Chaque fichier d'instructions définit les comptes requis par
cette instruction ainsi que la logique du gestionnaire qui s'exécute après
qu'Anchor a validé ces comptes.

```rust title="programs/my-program/src/instructions.rs" -w
pub mod initialize;
pub mod increment;

pub use initialize::*;
pub use increment::*;
```

<Note>
  **`pub mod initialize`**

  Les lignes _rs`pub mod`_ intègrent `src/instructions/initialize.rs` et
  `src/instructions/increment.rs` au crate du programme.

  **`pub use initialize`**

  Les lignes _rs`pub use`_ réexportent les éléments publics de ces fichiers. Cela
  rend les structs de comptes d'instructions et les fonctions de gestionnaire
  disponibles via le module _rs`instructions`_.
</Note>

### initialize.rs

`initialize.rs` définit les comptes nécessaires à la création du compte
compteur, puis écrit les premières valeurs du compte. La struct
_rs`#[derive(Accounts)]`_ utilise les
[contraintes de compte](https://www.anchor-lang.com/docs/references/account-constraints)
Anchor pour spécifier quels comptes sont requis et comment le nouveau compte
compteur est créé.

```rust title="programs/my-program/src/instructions/initialize.rs" -w
use anchor_lang::prelude::*;

use crate::{constants::*, state::Counter};

#[derive(Accounts)]
pub struct Initialize<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,
    #[account(
        init,
        payer = payer,
        space = 8 + Counter::INIT_SPACE,
        seeds = [COUNTER_SEED],
        bump
    )]
    pub counter: Account<'info, Counter>,
    pub system_program: Program<'info, System>,
}

pub fn handle_initialize(ctx: Context<Initialize>) -> Result<()> {
    ctx.accounts.counter.count = 0;
    ctx.accounts.counter.authority = ctx.accounts.payer.key();

    let cpi_accounts = anchor_lang::system_program::Transfer {
        from: ctx.accounts.payer.to_account_info(),
        to: ctx.accounts.counter.to_account_info(),
    };
    let cpi_ctx = CpiContext::new(anchor_lang::system_program::ID, cpi_accounts);
    anchor_lang::system_program::transfer(cpi_ctx, HELLO_WORLD_LAMPORTS)?;

    msg!("Hello, world! Counter initialized");
    Ok(())
}
```

<Note>
  Ce fichier importe les constantes partagées et le type de compte _rs`Counter`_.
  L'instruction utilise ces définitions pour dériver le PDA, choisir le montant du
  transfert et allouer le compte avec la taille de données appropriée.

  **`derive(Accounts)`**

  _rs`Initialize`_ est le contexte de compte pour l'instruction _rs`initialize`_.
  Chaque champ dans la struct représente un compte distinct qui doit être inclus
  lorsque l'instruction est appelée. Anchor utilise la struct pour valider ces
  comptes entrants avant l'exécution du handler.

  **`#[account(mut)]`**

  _rs`#[account(mut)]`_ indique à Anchor que le compte payeur doit être accessible
  en écriture. Cela est obligatoire car la création de compte et le CPI de
  transfert déduisent tous deux des lamports du payeur.

  **`Signer<'info>`**

  _rs`Signer<'info>`_ indique à Anchor que le payeur doit signer la transaction.

  **`#[account(`**

  Le bloc _rs`#[account(...)]`_ indique à Anchor comment créer et valider le
  compte compteur avant l'exécution du handler.

  **`init`**

  _rs`init`_ indique à Anchor de créer le compte _rs`counter`_ avant l'exécution
  du handler. Le nouveau compte appartient à ce programme, qui peut donc y stocker
  des données de type _rs`Counter`_.

  **`payer = payer`**

  _rs`payer = payer`_ désigne le compte _rs`payer`_ comme payeur pour la création
  du nouveau compte compteur.

  **`space = 8 + Counter::INIT_SPACE`**

  _rs`space = 8 + Counter::INIT_SPACE`_ alloue les octets nécessaires pour le
  discriminateur de compte d'Anchor ainsi que pour les champs _rs`Counter`_ issus
  de `state.rs`. Le discriminateur permet à Anchor de confirmer que le compte
  contient le type attendu avant de le lire.

  **`seeds = [COUNTER_SEED]`**

  _rs`seeds = [COUNTER_SEED]`_ indique que l'adresse du compte compteur doit être
  le PDA dérivé de ce seed et de l'ID du programme. Avec un seul seed fixe, il
  n'existe qu'un seul PDA compteur pour ce programme. Pour créer des compteurs
  distincts dans un programme réel, vous ajouteriez généralement un autre seed,
  tel que l'adresse d'un utilisateur.

  **`bump`**

  _rs`bump`_ demande à Anchor de trouver et valider le bump du PDA, c'est-à-dire
  l'octet supplémentaire qui rend l'adresse dérivée valide en tant que PDA.

  **`Account<'info, Counter>`**

  _rs`Account<'info, Counter>`_ demande à Anchor de traiter les données du compte
  comme étant de type _rs`Counter`_ issu de `state.rs`. Anchor vérifie également
  que le compte appartient à ce programme.

  **`Program<'info, System>`**

  _rs`Program<'info, System>`_ exige que l'appelant fournisse le System Program.
  Anchor l'utilise pour la contrainte de création de compte _rs`init`_. Le CPI de
  transfert du handler invoque également le System Program.

  **`handle_initialize`**

  Le handler s'exécute après qu'Anchor a validé les comptes et créé le compte
  compteur, ce qui lui permet d'écrire les données initiales du compte en toute
  sécurité.

  **`counter.count = 0`**

  Définit le champ _rs`count`_ du compte compteur à _rs`0`_.

  **`counter.authority = ctx.accounts.payer.key()`**

  Définit le champ _rs`authority`_ du compte compteur à l'adresse du payeur.

  **`system_program::Transfer`**

  Ce sont les comptes transmis à l'instruction de transfert du System Program. Ce
  CPI de transfert est inclus uniquement pour illustrer comment un CPI transmet
  des comptes à un autre programme.

  **`CpiContext::new`**

  _rs`CpiContext`_ regroupe le programme cible et les comptes requis pour une
  Cross Program Invocation. La création du contexte prépare le CPI en associant le
  programme que vous souhaitez appeler avec les comptes attendus par ce programme.

  **`system_program::transfer`**

  Ce CPI invoque l'instruction de transfert du System Program et déplace
  _rs`HELLO_WORLD_LAMPORTS`_ du payeur vers le compte compteur.

  **`msg!`**

  _rs`msg!`_ écrit un message dans les journaux du programme lorsque celui-ci est
  invoqué.
</Note>


### increment.rs

`increment.rs` définit les comptes requis pour mettre à jour un compte compteur
existant. Le handler vérifie que le signataire est l'autorité enregistrée,
vérifie que le compteur n'a pas atteint la valeur _rs`MAX_COUNT`_ spécifiée,
puis incrémente le compteur.

```rust title="programs/my-program/src/instructions/increment.rs" -w
use anchor_lang::prelude::*;

use crate::{constants::*, error::ErrorCode, state::Counter};

#[derive(Accounts)]
pub struct Increment<'info> {
    #[account(
        mut,
        seeds = [COUNTER_SEED],
        bump
    )]
    pub counter: Account<'info, Counter>,
    pub authority: Signer<'info>,
}

pub fn handle_increment(ctx: Context<Increment>) -> Result<()> {
    require_keys_eq!(
        ctx.accounts.counter.authority,
        ctx.accounts.authority.key(),
        ErrorCode::Unauthorized,
    );
    require!(
        ctx.accounts.counter.count < MAX_COUNT,
        ErrorCode::CounterOverflow,
    );

    ctx.accounts.counter.count += 1;
    msg!("Hello, world! Counter is now {}", ctx.accounts.counter.count);
    Ok(())
}
```

<Note>
  **`derive(Accounts)`**

  _rs`Increment`_ est le contexte de compte pour l'instruction _rs`increment`_.
  Anchor l'utilise pour valider le compte compteur mutable et le signataire
  requis.

  **`mut`**

  _rs`mut`_ indique à Anchor que le compte compteur doit être accessible en
  écriture, car le handler met à jour la valeur _rs`count`_ stockée.

  **`seeds = [COUNTER_SEED]`**

  _rs`seeds = [COUNTER_SEED]`_ vérifie que le compte compteur fourni est bien le
  PDA dérivé de ce seed et de l'ID du programme.

  **`bump`**

  _rs`bump`_ indique à Anchor de trouver et de valider le bump PDA pour le compte
  compteur.

  **`Account<'info, Counter>`**

  _rs`Account<'info, Counter>`_ indique à Anchor de désérialiser les données du
  compte en tant que type _rs`Counter`_ depuis `state.rs`. Anchor vérifie
  également que le compte appartient à ce programme.

  **`Signer`**

  _rs`Signer`_ exige la signature de l'autorité. Le handler compare ensuite
  l'adresse de ce signataire à l'autorité stockée dans le compte compteur.

  **`handle_increment`**

  Le handler s'exécute après qu'Anchor a validé la liste des comptes, vérifié la
  propriété et désérialisé le compte compteur.

  **`require_keys_eq!`**

  _rs`require_keys_eq!`_ compare deux clés publiques et interrompt l'instruction
  si l'adresse du signataire ne correspond pas à l'autorité stockée dans le compte
  compteur. Il s'agit de la règle d'autorisation au niveau applicatif de ce
  modèle.

  **`require!`**

  _rs`require!`_ vérifie une règle booléenne et interrompt l'instruction avec
  _rs`CounterOverflow`_ si le compteur a déjà atteint _rs`MAX_COUNT`_. Cette règle
  de modèle illustre les erreurs personnalisées et l'échec avant mutation.

  **`count += 1`**

  Ce n'est qu'après la réussite des deux vérifications que le handler met à jour
  les données du compte compteur. Si l'une ou l'autre échoue, la transaction
  échoue et le compte n'est pas modifié.

  **`msg!`**

  _rs`msg!`_ écrit un message dans les journaux du programme lorsque celui-ci est
  invoqué.
</Note>

```rust title="programs/my-program/tests/test_initialize.rs" -w
use {
    anchor_lang::{
        prelude::Pubkey,
        solana_program::{instruction::Instruction, system_program},
        AccountDeserialize, InstructionData, ToAccountMetas,
    },
    litesvm::LiteSVM,
    solana_keypair::Keypair,
    solana_message::{Message, VersionedMessage},
    solana_signer::Signer,
    solana_transaction::versioned::VersionedTransaction,
};

#[test]
fn test_initialize() {
    let program_id = my_program::id();
    let payer = Keypair::new();
    let counter = Pubkey::find_program_address(
        &[my_program::constants::COUNTER_SEED],
        &program_id,
    )
    .0;
    let mut svm = LiteSVM::new();
    let bytes = include_bytes!(concat!(
        env!("CARGO_TARGET_TMPDIR"),
        "/../deploy/my_program.so"
    ));
    svm.add_program(program_id, bytes).unwrap();
    svm.airdrop(&payer.pubkey(), 1_000_000_000).unwrap();

    let instruction = Instruction::new_with_bytes(
        program_id,
        &my_program::instruction::Initialize {}.data(),
        my_program::accounts::Initialize {
            payer: payer.pubkey(),
            counter,
            system_program: system_program::ID,
        }
        .to_account_metas(None),
    );

    let blockhash = svm.latest_blockhash();
    let msg = Message::new_with_blockhash(&[instruction], Some(&payer.pubkey()), &blockhash);
    let tx = VersionedTransaction::try_new(VersionedMessage::Legacy(msg), &[&payer]).unwrap();

    let res = svm.send_transaction(tx);
    assert!(res.is_ok());

    let counter_account = svm.get_account(&counter).unwrap();
    let mut data: &[u8] = &counter_account.data;
    let counter_state = my_program::state::Counter::try_deserialize(&mut data).unwrap();
    assert_eq!(counter_state.count, 0);
    assert_eq!(counter_state.authority, payer.pubkey());

    let instruction = Instruction::new_with_bytes(
        program_id,
        &my_program::instruction::Increment {}.data(),
        my_program::accounts::Increment {
            counter,
            authority: payer.pubkey(),
        }
        .to_account_metas(None),
    );

    let blockhash = svm.latest_blockhash();
    let msg = Message::new_with_blockhash(&[instruction], Some(&payer.pubkey()), &blockhash);
    let tx = VersionedTransaction::try_new(VersionedMessage::Legacy(msg), &[&payer]).unwrap();

    let res = svm.send_transaction(tx);
    assert!(res.is_ok());

    let counter_account = svm.get_account(&counter).unwrap();
    let mut data: &[u8] = &counter_account.data;
    let counter_state = my_program::state::Counter::try_deserialize(&mut data).unwrap();
    assert_eq!(counter_state.count, 1);
    assert_eq!(counter_state.authority, payer.pubkey());
}
```

<Note>
  **`litesvm::LiteSVM`**

  _rs`LiteSVM`_ est une VM Solana en cours de processus destinée aux tests. Elle
  permet au test d'enregistrer le programme compilé, de créer des comptes,
  d'envoyer des transactions et d'inspecter l'état des comptes sans démarrer un
  processus validator.

  **`let program_id`**

  Le test récupère l'adresse du program account à partir de la valeur
  _rs`declare_id!`_ via _rs`my_program::id()`_ et crée un nouveau keypair payeur
  pour la transaction de test.

  **`Pubkey::find_program_address`**

  L'adresse du compteur est dérivée du même _rs`COUNTER_SEED`_ utilisé par le
  programme. Cela permet au test de cibler le PDA qu'`initialize.rs` attend.

  **`include_bytes!`**

  _rs`include_bytes!`_ lit le fichier `my_program.so` compilé produit par la
  compilation. Ces octets constituent le code exécutable du programme que LiteSVM
  exécutera lors du test.

  **`svm.add_program`**

  _rs`svm.add_program`_ enregistre les octets du programme compilé à l'adresse du
  programme dans LiteSVM. Le parachutage donne au payeur suffisamment de SOL local
  pour payer la transaction et la création du compte.

  **`let instruction`**

  _rs`Instruction::new_with_bytes`_ crée une instruction pour invoquer le
  programme. Elle inclut l'ID du programme, les instruction data et les comptes
  d'instruction.

  **`svm.latest_blockhash`**

  Chaque transaction Solana nécessite un blockhash récent. Dans ce test, LiteSVM
  fournit un blockhash à utiliser pour la transaction.

  **`Message::new_with_blockhash`**

  Le message contient l'instruction, le payeur des frais et le blockhash. Ce sont
  les données de transaction qui seront signées.

  **`VersionedTransaction::try_new`**

  _rs`VersionedTransaction::try_new`_ signe le message avec le keypair du payeur.
  Le payeur signe car il règle les frais de transaction et finance le nouveau
  compte compteur.

  **`svm.send_transaction`**

  _rs`svm.send_transaction`_ exécute la transaction dans LiteSVM.

  **`svm.get_account`**

  Une fois la transaction exécutée, le test lit le compte compteur directement
  depuis LiteSVM afin d'inspecter les données du compte.

  **`Counter::try_deserialize`**

  Le compte compteur stocke des données sérialisées.
  _rs`Counter::try_deserialize`_ vérifie le discriminateur de compte d'Anchor et
  reconvertit les données du compte en type _rs`Counter`_ depuis `state.rs`.

  **`assert_eq!(counter_state.count, 0)`**

  Une fois _rs`initialize`_ réussi, le test désérialise le compte compteur et
  vérifie que l'état initial correspond à ce que _rs`handle_initialize`_ a écrit.

  **`assert_eq!(counter_state.count, 1)`**

  Une fois _rs`increment`_ réussi, le même compte compteur devrait avoir
  _rs`count`_ défini à _rs`1`_ tout en conservant la même autorité.
</Note>

## Configuration du projet

Les fichiers racine du projet indiquent à Anchor et à Cargo comment compiler,
tester et déployer le programme. Pour une référence complète, consultez la
documentation Anchor pour la
[configuration Anchor.toml](https://www.anchor-lang.com/docs/references/anchor-toml)
et l'[Anchor CLI](https://www.anchor-lang.com/docs/references/cli).

```toml title="Anchor.toml"
skip_local_validator = true

[toolchain]

[features]
resolution = true
skip-lint = false

[programs.localnet]
my_program = "82sFkffP9wxwpyfZyeaKHH2chQoJPUGsJZSPi9mrUuXd"

[provider]
cluster = "localnet"
wallet = "~/.config/solana/id.json"

[scripts]
test = "cargo test"

[hooks]
```

<Note>
  **`skip_local_validator`**

  `skip_local_validator = true` indique à Anchor de ne pas démarrer un validator
  pour `anchor test`. Le test Rust utilise LiteSVM à la place.

  **`programs.localnet`**

  `[programs.localnet]` associe le nom de la crate Rust à l'adresse du programme
  utilisée pour les builds et les tests locaux.

  **`provider`**

  `[provider]` définit le cluster et le portefeuille par défaut pour les commandes
  telles que `anchor deploy`.

  **`scripts`**

  `[scripts]` modifie ce que `anchor test` exécute. Dans ce modèle, `anchor test`
  exécute `cargo test`.
</Note>
